开发者定下的方向（不要改回）：

- 第一批检索词由独立的 AI 调用来写；代码不机械地从问题里取词（取出来的是句子碎片，靠加分支修只会让代码变杂）。
- 照搬台词不用代码把关，只在提示词里要求“不要大段照搬”。
- 答案被退回时，出错的内容不进上下文、不在界面长期保留，只显示一行“回答格式出错，正在重新构思回答…”。
  （重问时附的那条纠正说明是实现时加的，不是开发者的要求：不带说明的重试会原样重犯；答案被接受后它会从对话里拿掉。）
- 各工具的“已读”口径统一；提示词每条规则一个出处、按角色组合，留在 Dart 里，不做成运行时读取的外部文件。

与当初计划不同的五处（都已向开发者说明）：

1. 拟定出检索词时，不再另外用问题原文做一次向量检索（那样每问最多四份结果进上下文）；问题原文的检索只在拟定失败且有向量时作退路。
2. 工作过程里没有单独的“拟定检索词”一步，只有随后的几条检索步骤（各自显示检索词）。界面上分不出哪几条是拟定的，会话记录里能分清。
3. 略去另一个游戏的条件除了“意思明显更远”，还要求关键词命中不比另一个游戏多。
4. 没有用真机会话的原始数据做重放夹具（需要真实知识库）；对应的三个行为用虚构夹具各有一个用例。
5. 界面文案 `aiWorkRedo`（“重写答案”）不再被引用，没有删（删它要重新生成本地化文件）。

## 3. 真机测试工具（桥）能看到什么、看不到什么

`tools/phone_ask.dart` 通过 `lib/features/ai/phone_bridge.dart` 拿到的是 App 的问答状态（步骤、思考、状态行、答案文本、用量），不是屏幕。
把 2026-10-10 的截图和终端日志对照后的结论：

**一致的**（可以信终端）：

- 用量一行：`in 38.5k · out 1.2k · cache 61% · 4 calls · 44s` 与 `in 159k · out 2.2k · cache 77% · 8 calls · 1m27s`，截图与终端相同。
- 步骤的种类、顺序、参数；思考文字；最终答案的文字和出处。
- 截图里的“查阅 4 次 · 读了 0 篇”“查阅 15 次 · 读了 6 篇”能从终端的步骤数出来：查阅 = 全部工具调用（**含拟定的那几条检索**）；
  读了 N 篇 = `read_story` 读过的**不同故事数**（第二问调用 9 次，是 6 篇）。

**终端看不到的**（要看这些只能看屏幕或截图）：

- 汇总行本身（“已作答 · 查阅 N 次 · 读了 N 篇”）：桥不发这一行，要自己从步骤数。
- 出处的呈现：界面把出处显示成带故事名的出处卡，底部有“证据 N 条 · 来自 N 个故事”；终端只有反引号里的原始出处，看不出故事名有没有解析出来、卡片能不能点开。
- 答案的排版与折叠：流式过程中答案前面带着 `[DETAILS]` 标记，界面会把标记之后的内容折成一行“详细经过 · N 条”；终端显示的是原始文字。
- 思考面板的样子（固定高度、结束后是否保留）、状态行在屏幕上停留多久、滚动行为。

**终端与界面不一样的**（终端会误导）：

- 全库 `grep`（只返回分布）的结果：终端显示“0 处，0 篇”，界面上这一步**不显示数量**。两边用同一个解析（`WorkStep.grepCounts`，只认“## 故事（N 处）”的格式），
  桥在数量为 0 时仍然打印，界面则留空。实际结果是 32 行 / 16 篇，模型拿到的是对的。

## 5. 遗留问题（按建议的先后）

### 确定存在、值得先做

1. **关键词扫描慢，并行时更慢。** 单次检索里 `search:keywords` 约 2.2–2.5 秒，三条并行时每条 5.3 秒；终末地的库小得多，耗时却和明日方舟几乎一样，像是在同一个连接上排队（**未查代码确认**）。
   入口：`SearchTool._rank` → `searchStoryLinesLike`（`lib/core/gamedata/story_line_search.dart`）。先确认是不是排队，再考虑每个游戏/每条检索用各自的只读连接，或合并多条检索的扫描。
2. **流式作答时答案可能一直是折叠的。** 循环在流式输出前总是先发 `[DETAILS]` 标记（`lore_agent_loop.dart`，`live = '$loreDetailsMarker…'`），界面按标记把后面的内容折成一行；
   “提要”关着时没有上半部分，玩家在作答的二三十秒里可能只看到一行“详细经过 · N 条”，直到最后整体替换。**这是读代码得出的推断，没有在屏幕上确认**；先在手机上看一眼流式过程，属实再改（提要关着时不发标记）。
3. **全库 `grep` 的步骤不显示数量。** `WorkStep.grepCounts` 加上对“全库共 N 行命中，分布在 M 个故事”的解析；桥在解析不出时不要打印“0 处，0 篇”。

### 需要先查原因

4. **有的检索没有略去终末地**（8 次里 2 次）。规则是：最接近的段落比另一游戏远 0.08 以上、且关键词命中行数不比它多才略去。这两次是差值不够还是命中更多，没有查。
5. **拟定的检索词不够准。** 会带进不相干的名字。没有量过它的命中率（代码切词在评测集上是 16/29，那条路已删）。量一次要约 29 次小调用，**花钱，要先问开发者**。
   `loreSearchPlanPrompt` 里“可以用你对作品的了解补上相关名字”一句可能是原因，改之前先有数据。

### 没有在真机上验证过的新路径

6. 答案退回后的整轮回档（界面只显示一行状态、思考回退）与出处裁剪：两次真机问答都没有触发，只有离线用例（`lore_agent_loop_test.dart`、`agent_provider_test.dart`）。
7. 没有向量服务时的拟定检索、拟定失败的退路、较弱的模型（`tools/garbage_api_info.txt` 的 gemini）写检索词的水平：都没有用真实模型跑过。

### 已知、暂不处理

8. 出处只核对“看没看过”，不核对那几行是否支持那句话（编造、张冠李戴、接受提问里的错误前提）。审稿默认关，是开发者的决定。
9. 模型输出里的杂质（混入外文词、把名字写错一个字）没有检查。
10. 总耗时没有因为这轮改动下降（44 秒 / 87 秒，改前 47 秒 / 90 秒）。
11. 安装脚本 `tools/install_local.ps1` 最后“自动打开 App”一步在 PowerShell 5.1 下总是报失败（adb 的普通输出被当成错误），安装本身是成功的。

## 6. 接手时要知道的做法

- 花钱的事（真实 API、向量嵌入）先问开发者；每个方面最多 2 个用例，逐题串行，看完一题再跑下一题。
- 电脑上的 live 测试（`test/live/ask_pipeline_live_test.dart`）不是真机测试，汇报时要分清。
- 真机：`.\tools\install_local.ps1 -Build -Bridge`，然后 `dart run tools/phone_ask.dart --new "问题"`；不带 `--new` 是在同一会话里追问。
  不要替开发者解锁手机；电脑看不到手机时让开发者检查数据线、USB 用途（文件传输）和 USB 调试。
- 提交：作者只有 hhikr，不加任何 AI 署名；提交前 `git checkout -- android/gradle.properties`；`tools/garbage_api_info.txt` 不提交。
- PowerShell 5.1 里含中文弯引号（“ ”）的字符串会被当成引号截断，改这类文本用编辑工具或脚本文件，不要写在命令行里。
- 改提示词时：每条规则只在一处（`lore_agent_prompts.dart` 的各节），不放具体人物/章节名，有守卫测试。
