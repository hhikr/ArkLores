## 0. 接手后要做的工作：让工具说出“这个词在哪几部故事里”

### 0.1 背景

两类问题暴露了同一个缺口：模型手里有一个名字，却不知道它在库里的哪些地方。

- 按故事集来问的（“某个故事集之前发生了什么”）：上一轮已修，`outline` 末尾列出相关的故事集。
- 按人物来问的（“某位干员的经历”）：`search` 对一个有上千行命中的名字只给 5 章，模型看不到它还出现在哪几部，常漏掉其中一部。
  现在偶尔能找到，是因为模型碰巧看了某个目录、在“相关的故事集”里看到了它。

这一轮调查了全部 10 个工具，结论是做下面三项改动，按顺序做。调查的经过、每个数是怎么定的、被否定的方案，
在本机 `notes/tool_rag_linkage.md`（不进仓库；在这台开发机上能读到，读不到也不影响实施，规格都在这里）。

**动手前先问开发者两件事**：

1. 工作区里有上两轮没提交的改动（§1），要不要先提交。
2. 三项是否都做。调查的建议是：改动一必做；改动二、三价值较小（理由见各节），开发者说过“所有工具改动”都实施，但没有逐项确认过。

### 0.2 改动一（必做）：`search` 和 `grep` 写出命中按故事集的分布

**做完的样子。** `search` 结果开头，每个关键词一行（示意，尖括号是占位）：

```
检索“<query>”：按意思检索 + 关键词
关键词：
<词>（<N> 行，<K> 个故事集：<故事集> <n> 行 / <c> 章、<故事集> <n> 行 / <c> 章…；占比高的：<故事集> <n> 行（占该篇 <p>%）；另 <M> 个共 <q>%）
<词>（<N> 行，1 个故事集：<故事集> <n> 行 / <c> 章）
<词>（0 行，原文里没有这个写法）
```

`grep` 不带范围时（全库统计），在逐章列表前加一行：

```
全库共 <N> 行命中，分布在 <S> 章、<K> 个故事集：<故事集> <n> 行 / <c> 章、…；另 <M> 个共 <q>%
```

**规则**（所有词同一个格式，不判断“列还是不列”；常量集中定义、注释写明来源是 2026-10-11 的实测）：

1. 把命中的行按故事集分组，按行数从多到少排。
2. 依次列出，直到累计达到全部命中的 **80%** 或已列 **6** 个，哪个先到算哪个。
3. 没列出的里面，再补最多 **2** 个“占比高的”，三个条件同时满足：
   - 至少 **10** 行；
   - 这个词占那个故事集 **10%** 以上的行；
   - 这个比例是它在全库平均比例（全部命中行 ÷ 全库总行数）的 **5** 倍以上。
   按占比从高到低取。第三个条件是为了挡住到处都有的词，不要去掉。
4. 其余的写“另 M 个共 q%”。只有一个故事集、或全部列完时不写这一段。
5. 0 行的两种说法（“原文里没有这个写法”“这是故事集的名字”）保持现在的文字。

**分组用的“故事集”**：

- 先按 `story_catalog.collection_id`，名字用 `StoryCatalogEntry.collectionLabel` 的写法。
- 有约 1650 篇剧情不在 `story_catalog` 里（教程、集成战略、生息演算、部分活动的关卡内对话），其中绝大多数在 `entries`（id 为 `story:<story_id>`）里有条目和
  `collection_id`：按那个集合归类，名字取 `collections.name`。两处都没有的归到“其他”。
- 每个故事集的总行数（算占比用）和全库总行数：一条 `SELECT story_id, COUNT(*) FROM story_lines GROUP BY story_id`，随连接缓存，
  和 `_centroids` 一样在关闭连接处清掉。

**要改的地方**：

| 文件 | 改什么 |
|---|---|
| `lib/core/gamedata/story_line_search.dart` | `queryStoryLinesLike` 的第一条查询现在只数每个词的总行数。改成同一次扫描按 `story_id` 分组（加 `WHERE` 任一词命中），得到“每个词在每章多少行”，由一个新的可选出参带回（如 `Map<String, Map<String, int>>? termStories`）；`termLines` 照旧是它的合计。全库总行数另用一条 `COUNT(*)`。 |
| `lib/core/gamedata/story_catalog.dart` | 一个纯函数（无 IO，便于单测）：输入“每章多少行”、章到故事集的映射、各故事集总行数、全库总行数，输出分布（列出的、占比高的、其余的个数和占比）。常量放这里。 |
| `lib/core/gamedata/game_retrieval.dart`、`gamedata_knowledge_store.dart`、`multi_game_retrieval.dart` | `searchStoryLinesLike` 透传新出参；新增按上面规则算分布的方法。两个游戏都装着时各算各的（占比、倍数都在各自的库里算）。测试里实现这个接口的假对象补上。 |
| `lib/core/agent/tools/search_tool.dart` | `_termCounts` 改成每个词一行并带分布。带 `collection` 参数的检索不写分布（保持“全库 N 行”）。两个游戏都有命中时每个游戏一段，段首写游戏名。说明文字里“结果开头列出每个词命中多少行”补上“和分布在哪些故事集”。开头这几行不要挤掉下面的原文：`maxChars` 的判断只算原文块。 |
| `lib/core/agent/lore_tools.dart` | `GrepTool._corpusCounts`：`storyLineHitCounts` 已经是按章的数，用同一个函数加汇总行。说明文字相应补一句。 |

**不要做的**：

- 不登记进 `SeenLines`（分布不是读过的原文）。
- 不按词的种类分支（人名、地名一视同仁），不写名单，`lib/` 里不出现具体名字。
- 不在提示词里加新规则；需要的话只改这两个工具自己的说明。
- 不加表。

**测试**：

- 纯函数：80% 先到、6 个先到、只有一个故事集、“占比高的”三个条件各差一点时不补、其余的个数与占比、不在目录里的章按条目的集合归类、都没有时归“其他”。
- 夹具库：改后的 `termLines` 与改前相等；每章的数加起来等于总数。
- `search` 的输出：每个词一行、有分布；带 `collection` 时没有；0 行的两种说法不变。`grep` 全库统计多一行汇总。
- 真实库的免费检查（`test/live/gamedata_v5_acceptance_test.dart`，`ARKLORES_RUN_DB_CHECK`）：加一项，按环境变量点名几个词打印分布和耗时，
  断言列出的不超过 6 + 2、各项行数之和不超过总数、不重复。哪些故事集排在前面只看输出，不写进断言。
- 守卫测试照常（提示词无具体名字、无特判）。

**耗时的预期**（调查时在电脑上用 SQLite 直接量的）：第一条查询 1 个词 123 → 158 毫秒，8 个词 715 → 790 毫秒。
实现后看会话 `timeline` 里的 `search:keywords:*`，和改前（`build/live_sessions/` 里已有的会话）比；明显变慢先查原因再继续。

### 0.3 改动二：`search` 可以用一段读过的剧情作查询

**做完的样子。** `search` 多一个可选参数（如 `near`），写一个位置 `<story_id>:<行号>`；有它时不需要 `query`：

```
检索与《<故事名>》L<a>-<b> 相近的段落（按意思）：
1. 《<故事名>》 <story_id>（意思相近 0.xx）
   L<n> [<说话人>] <原文>
   …（8 行）
2. …
（只列相近程度 0.70 以上的，每个故事集一段，最多 5 段；这一段所在的故事集不列）
```

一条都没有时写“别处没有与这一段相近的段落”。

**规则**：

- 用库里已存的那一块向量去比，**不调嵌入服务**（没有配置向量服务、但库里有向量时也能用）。
- 位置落在几块里时取包含那一行的第一块（剧情每 12 行一块、每 8 行起一块）。那一章没有向量时如实说。
- 排除同一个故事集；每个故事集只留最近的一块；只留 **0.70** 以上；最多 **5** 段。只在同一个游戏的库里找。
- 列出的 8 行原文照常登记为已读（它们是展示过的原文）。

**要改的地方**：`story_vectors.dart`（按位置取块、以库内向量为查询的最近邻）、`game_retrieval.dart` 及两个实现、`search_tool.dart`（参数、渲染）。
`query` 现在是必填，工具调用守门（`tool_call_gate.dart`）按 `required` 检查：改成两者至少给一个时，守门和它的“正确写法”提示要一起改，并补用例。

**0.70 的来历**：随机 500 段、每段取别的故事集里最近的 5 段，以“两个故事集有共同的、不是到处都有的说话人”近似判断相关：
0.70 以上约九成相关，0.65–0.70 约六成，再往下约三成半。改这个数之前先在真实库上重看。

**为什么排第二、价值较小**：`outline` 的相关故事集和改动一的分布已经能把模型引到别的故事去；这一项是“这件事在别处有没有呼应”的补充。
不要把它做成 `read_story` 末尾自动附带的内容（那是调用最多的工具，每次都加字会拖累后面每一轮）。

### 0.4 改动三：`read_record` 开头写出所属对象的名字分布

**做完的样子。** 有“所属对象”的资料，第一页（`start` 为 0）的标题行下面多一行，格式和改动一完全相同（同一个函数）：

```
record:<id> | <类别> | <标题> | 所属：<对象>
“<对象>”在剧情里：<N> 行，<K> 个故事集：…；另 <M> 个共 <q>%
<正文>
```

**规则**：所属对象的名字来自记录本身（`RecordText.owner`，按表里的 id 填的），不从正文里找名字；名字不足 2 个字、或剧情里 0 行时不写这一行。
只是线索，不登记为已读。

**为什么排最后、价值较小**：

- 做了改动一之后，模型搜这个名字就能看到同样的分布，这里是重复，只省一次检索。
- 它要多扫一遍台词表：电脑上约 0.15 秒，**手机上按字面扫一遍要 1.3–6 秒**（§6 第 1 条的旧数据）。
  做之前先量手机或至少在电脑上量 `tool:read_record` 的耗时变化，并向开发者说明这个代价；同一次问答里同一个名字的分布要缓存。

**不要做的**：不要用向量去找“与这份资料相近的剧情”。调查时在 150 份干员档案上测过：最好的规则也只找回六成、列出的里有一成半是错的
（每份档案都有体检、诊断一类的小节，和讲医疗的几部故事对谁都近），短资料更差（有真值的 975 条里只有四成把自己所属的活动排第一）。

## 4. 开发者定下的方向（不要改回）

- Wiki 与本地库检索同级，答案仍区分来源；以向量检索为主，没有向量服务时退回关键词并提示“问答质量可能下降”；审稿与子助手默认关闭。
- 提要与复核是答案下方的按钮，不是提问的选项；复核的结果接在下面、原答案不动；两者只对本次运行期间的答案有。
  深度思考收进选项面板、只在服务商有思考开关时显示。知识库页每个游戏一页；“用游戏数据更新”保留。
- **（10-10 夜）知识库里没人读的东西要删，从建库和更新开始删**：被删的表与“覆盖层”不要加回来；加一张表之前先写清谁读它，
  读它的代码删了，表和建它的步骤一起删。
- **（10-10 夜）手机上的验证由开发者自己做**：把库和包装好、说明要点哪里即可；不要为了“看一眼”替他在手机上跑更新。
- 第一批检索词由独立的小调用来写；代码不从问题里切词、找名字（切出来的是句子碎片，靠加分支修只会让代码变杂）。
- 照搬台词不用代码把关，只在提示词里要求“不要大段照搬”。
- 答案被退回时，出错的内容不进上下文、不在界面保留，只显示一行“回答格式出错，正在重新构思回答…”。
  （重问时附的那条纠正说明是实现时加的，不是开发者的要求：不带说明的重试会原样重犯；答案被接受后它会从对话里拿掉。）
- 各工具的“已读”口径统一（`SeenLines`）；提示词每条规则只写一处、按角色组合，留在 Dart 里。
- 两个库的所有资料都要有向量：每条记录一个，长文按小节切。
- “读了 N 篇原文”数所有工具展示过正文的故事；“查阅 N 次”含拟定的检索；“证据 N 处 · 来自 N 个故事”不变。
- 没有覆盖到或有歧义的地方先问开发者，不要自己假设；不要把范围扩到讨论过的内容之外。
- 明确说过暂不做：同一批检索结果去重、“回到底部”按钮的位置、§6 的“已知、暂不处理”各条。

## 6. 遗留问题

### 确定存在

1. **关键词扫描是检索里最慢的一段。** 手机上每个库 1.3–6.3 秒（并行的检索更慢）；Wiki 0.5–12 秒；剧情向量 0.08–0.2 秒；资料向量 0.13–0.66 秒。
   终末地的库小得多，耗时却和明日方舟接近，像是在同一个连接上排队（**没有查代码确认**）。
   入口：`SearchTool._rank` → `searchStoryLinesLike`（`lib/core/gamedata/story_line_search.dart`）。先确认是不是排队，再考虑各用各的只读连接、
   合并扫描，或 §2 第 3 条的中文全文索引。这些数是瘦身前量的；库小了以后没有重新量。
2. **路径写短的出处被删**（§2 第 4 条）。
3. **拟定的检索词带资料种类的词和泛名字**（§2 第 5 条）。评测集上的命中是 25/29（带向量）。
4. **长整理题很贵。** “整理某人在主线第 9–15 章的主要行动”全程只用 `grep`（16 次）、没有 `read_story`，输入 27.8 万 token、100 秒；答案七章都有小节和出处。
5. **答案正文偶尔提到“知识库”**（不存在的角色那题），违反“正文不提库”的约定。只见到一次。
6. **“读了 N 篇”偏大**：检索结果里列出的原文行也算，一次检索就能让这个数到十几。口径是开发者定的，记一笔。
7. **“回到底部”按钮盖住正文右缘**两三行的行尾（`ai_chat_page.dart`，`scroll-to-bottom`）。开发者说过这轮不改；要改先问想要的样子。
8. **手机上的源目录标记可能与库不一致**：`gamedata_source/.source_commit` 记的是上一次更新到的提交，库被换回官方版本后两者不同。
   `SourceSync.sync` 发现不一致时会删掉本地的表重新取（已有的行为，手机上那次成功的更新走的就是这条路），只是多下载约 60 MB 的上下文表。

### 已知、暂不处理

9. 出处只核对“看没看过”，不核对那几行是否支持那句话（编造、张冠李戴、接受提问里的错误前提）。审稿默认关，是开发者的决定。
10. 模型输出里的杂质（混入外文词、把名字写错一个字）没有检查。GLM 在“思考”关着时仍会输出英文的思考文字，界面照样显示。
11. 调 `tools/install_local.ps1` 时**不要加 `2>&1`**：PowerShell 5.1 会把 adb 写到 stderr 的普通进度当成错误，脚本在 `adb push` 之后或
    “自动打开 App”一步中止，而安装其实成功了。不加重定向时脚本正常结束（脚本末尾启动 App 那一步已改成只看退出码）。

## 7. 真机测试

### 提问

`.\tools\install_local.ps1 -Build -Bridge` 装带桥的包，然后 `dart run tools/phone_ask.dart --new "问题"`；不带 `--new` 是在同一会话里追问。
`/review`、`/digest` 当作问题发出去是按最后一条答案下方的那两个按钮。会话 JSON 拉到 `build/phone_sessions/`。
不要替开发者解锁手机；电脑看不到手机时让开发者检查数据线、USB 用途（文件传输）和 USB 调试。
adb 在 `C:\Users\hhikr\dev\android-sdk\platform-tools\adb.exe`。

### 把本机构建的知识库装到手机上

App 只认校验值与构建时写进去的一致的库，所以要连包一起装：

1. 把两个 `.gz` 的 SHA-256 临时写进 `tools/release_gamedata.env`，然后 `install_local.ps1 -Build -Bridge -Kb -Ef`
   （`-Kb` / `-Ef` 把两个 gz 推到应用目录，文件名 `arklores_gamedata_zh.db.download.gz`、`arklores_endfield_zh.db.download.gz`）。
   **构建完立刻还原这个文件**（`git checkout -- tools/release_gamedata.env`，不提交）。
2. 安装：`dart run tools/phone_ask.dart --kb=install`（终末地加 `--game=endfield`）——等于在知识库页按“下载 / 更新 / 重新下载 / 换回官方版本”，
   应用目录里有那个 gz 时离线校验安装。最后一行会打印装上的库的大小、行数和上游提交。也可以让开发者在页面上点。
   由人来点时要等推送**完成后**再点：推送中途点了，App 会去下载旧资产、校验不过、把文件删掉，要重推。
3. 装好后 gz 会被用掉；要再装一次（比如把库换回 `a550f5e`）得重新推（`install_local.ps1 -KbOnly -Kb`）。
   同目录下的 `.asset_sha256` 标记应等于新的 SHA。

### 桥能按的知识库按钮

`dart run tools/phone_ask.dart --kb=status|install|check|update [--game=endfield] [--allow-full]`（`lib/features/ai/phone_bridge.dart` 的 `kb` 命令）。
`check` / `update` 是明日方舟页的“检查更新”“拉取并更新”，逐阶段打印进度，结束时打印更新报告和装上的库的状态。
**`update` 会改手机上的库，跑之前先问开发者。**

### 桥能看到什么

`tools/phone_ask.dart` 拿到的是 App 的状态，不是屏幕。要看屏幕用 `adb shell screencap`（App 在前台、手机亮着时），不要用 adb 去点开发者的手机，除非他同意。

- **可以信终端的**：步骤的种类、顺序、参数；思考文字；状态行；最终答案的文字和出处；用量一行；汇总行（“已作答 · 查阅 N 次 · 读了 N 篇”）；
  知识库命令打印的阶段、报告和库的状态。
- **终端看不到的**：出处卡（故事名有没有解析出来、能不能点开）、底部“证据 N 处 · 来自 N 个故事”、答案的排版与折叠、
  思考面板的样子（固定高度是既有设计）、状态行停留多久、滚动行为；知识库页上按钮的可用状态和文案。
- **界面上几个数的数法**：“查阅”= 全部工具调用，含拟定的检索；“证据 N 处”把同一篇里重叠的行段并成一处，资料算在内；
  “来自 N 个故事”指故事集，不是故事文件。所以它们和答案里不同出处的条数对不上是正常的。
- 检索内部各段的耗时在会话记录的 `timeline` 里（`search:keywords:*` 等），是 App 自己记的，不经过桥。

## 8. 接手时要知道的做法

- 花钱的事（真实 API、向量嵌入）先问开发者；每个方面最多 2 个用例，逐题串行，看完一题再跑下一题。
- 电脑上的 live 测试（`test/live/ask_pipeline_live_test.dart`）不是真机测试，汇报时要分清。
