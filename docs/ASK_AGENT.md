# 剧情问答 Agent

> 现在的流程（2026-10-26，0.20）。代号 R17 的工具型 Agent 从 v0.10.1 起是剧情问答唯一的流程，骨架没变过；
> 0.14 重做了外围，统一重构第 1–2 期（2026-10-18/19）加了按名字取材、追问重读、查证“没有查到”；
> 0.20 取消主 agent 的轮数上限，加了上下文用量、不重复读取、上下文压缩与对话完整保存（§6.5–6.7）。
> 每种做法为什么这样定、试过哪些别的、数据如何：`ASK_EXPERIMENTS.md`。仍开放的问题：`KNOWN_ISSUES.md` §2。模型服务的差异：`LLM_PROVIDERS.md`。

## 1. 原则

- **读原文的模型就是写答案的模型**：信息每多一次交接就丢一部分（分步流程的根本问题）。
- **工具要有表达力**：只读 SQL 一次看全语料；整章读、章内搜；0 命中如实报告并附近名。
- **对话只追加**：前缀缓存命中 80–90%；工具结果一直留在对话里，接近上下文提醒值时才整体压缩一次（§6.6）。
- **能确定地取到的原文由代码直接给**（“指路不如直接给”）：只告诉模型“还有哪里可以看”，它有一半时候不去。
- **不写手写进度规则**（预算提示、重读阶梯、阅读计划）。例外只有开发者定的三条：第一轮按名字取材一次（§3.2）、查证“没有查到”（§6.3）、没有结果的查找每个工具每问最多 6 次（§4.3）。
  0.20 的不重复读取（§6.5）只拦**此刻还在上文里**的原文与相同的调用，原文被压缩掉以后照样能重读，是去重而不是进度规则。
- **代码只做确定性的事**：出处是否被工具展示过、状态信封、核查结论降级、只读 SQL 的边界。
- **没有问题类型分支**：同一流程、同一份提示词；提示词与工具说明里不放具体人物/章节/活动/剧情手法（守卫测试）。
- 目录、梗概、向量、卡片都只是**定位线索**，不参与事实判定。

## 2. 一次问答怎么走

```
用户问题 ─► AskChatNotifier.sendMessage ─► StoryQaAgent.run ─► LoreAgentLoop
  0. 追问时：上下文到了压缩线先压缩（§6.6）；代码按上一答引用且读过、已不在上文的行段调用 read_story 重读（followUpReads）
  1. 拟定：一次独立的小调用（loreSearchPlanPrompt，不思考，最多等 25 秒，超时即中断请求）
     写出 ≤3 条检索词、≤2 个要看目录的故事集、≤2 个 Wiki 搜索词、≤6 个锚点
  2. 代码执行拟定的 search / outline / wiki_search（并行）
  3. 代码按锚点调用一次 gather（按名字取材，约 3 万字）
     ── 以上都作为普通的工具调用和结果进入对话，给出的行登记为已读 ──
  4. 主模型自己查：每轮发请求前估算上下文、到了压缩线先压缩 → streamTurn(tools) → 守门 → 去重（还在上文的不执行）
     → 同一轮的调用并发执行 → 结果按顺序追加（主 agent 不限轮数；子助手最多 10 轮）
  5. 最终答案（JSON）→ 出处核对（SeenLines：裁剪 / 删除 / 整轮退回）
  6. 查证“没有查到”：答案的 missing 里的名字再取材一次，有没读过的原文就交回重写一次
  7. 状态信封 [STORY_ANSWER: status=answered|partial|not_covered]
答完之后（答案下方的按钮，玩家点了才运行）：“提要” digestAnswer、“复核” reviewAnswer
```

- system：`loreRolePrompt`（作答 / 子助手 / 拟定 / 审稿 / 整理五种角色组合）：资料来源概览 + 工作方式 + 阅读原则 + 出处 + 答案格式。
  表与绑定、资料页结构在手册里（`guide` 工具，没看过时随第一条 `sql` 结果附上）。装了终末地时加“两个游戏”一节（`lore_endfield_prompts.dart`），开着 Wiki 时加 `loreWikiGuide`。
- messages：[上一问的完整对话，或压缩后的纪要（追问时）] + 用户问题 + 每轮 assistant/tool 消息。用户消息只有问题本身。
- 会话记录：`ChatSessionStore`（`chat_sessions/` 每对话一个 JSON：每次模型输出、工具、观察、答案、用量、分段计时、“记录”行，以及接着问所需的完整对话 `lore_conversation`）。

## 3. 第一批查找

### 3.1 拟定

第一次模型调用之前，一次独立的小调用只看问题（追问时加上一问和上一答的开头与小节标题）和各工具自己的说明，输出一个 JSON：
最多三条检索词、最多两个要看目录的故事集、最多两个 Wiki 搜索词（合计不超过四步）、一个附在第一条检索上的 Wiki 词，和最多六个锚点（`anchors`，不算在四步里）。
代码照着执行，工具不在（没开 Wiki）的步骤略过。超过 25 秒或写不出来：有向量就用问题原文按意思检索一次，没有向量就由主模型自己检索；超时的那次请求被中断（`abortTrigger`），不与主模型的请求并发。
**代码不从问题里切词、找名字**（切出来的是句子碎片）。

### 3.2 按名字取材（`gather`）

开发者 2026-10-18 定下，依据是离线召回测试（日志题第一步金标行 37% → 74%）。检索跑完后代码调用一次：

- 定位：每个锚点在剧情里说话（说话人相等）或被写到（正文含它）的行；单字的名字只按说话人找。
- 打分：锚点越少见权重越大（1/log2(2+篇数)），两个锚点相距 6 行以内算同场，同场加权最多；拟定的检索找到过的篇略加分。
- 选篇：每个故事集先最多三篇，再不限；每篇最多 3000 字，共约 3 万字；每处取前后各两行，优先同场的中心。
- 排列：按上线顺序（`storyReleaseKey`：活动的开始时间，否则剧情回顾的开放时间 `show_time`，再按主线章号）；没给原文的篇列成清单，另附最多 4 条资料片段。
  v0.14.0 的明日方舟库没有 `show_time`，主线因此排在所有活动之后；2026-10-19 起重建的库有。
- 给出的行都登记为已读。工作过程里这一步写“定位到 N 篇、给了 M 篇”。

它和“固定阅读步骤”不同：由代码做一次、结果只给一次，模型不执行清单。**改锚点、打分、预算之前先重跑召回测试**（`ASK_EXPERIMENTS.md` §1）；前后行数加大、挑行都试过，更差。

## 4. 工具

0.18 起，统一检索还覆盖资料页启用的补充资料。每问固定来源、正文版本及说明版本；`grep`、`gather`、`search(near)` 可联查游戏与资料，`read_material` 分页读原文，`sql(source="materials")` 只查本轮启用资料的快照。资料引用按版本、段号核对，使用与 Wiki／剧情相同的已读账本。来源说明保留在系统上下文，不能作为正文事实。详见 `MATERIALS.md`。

所有工具的结果上限 8k 字（`gather` 除外）。检索面是 `MultiGameRetrieval`：装了几个游戏的库就查几个，终末地的 id 以 `ef/` 开头。

| 工具 | 作用 |
|---|---|
| `search(query?, near?, collection?, game?, wiki?)` | 统一检索：`query` 按意思检索（有向量服务时），空格分开的词各自做关键词检索，RRF 融合；同时查剧情、资料和 Wiki，**按来源分组**。打印出的行记为已读 |
| `read_story(story_id, start, count)` | 连续读剧情原文，`L行号 [说话人] 内容`；默认 200 行、最多 300 行 |
| `read_record(id)` | 读剧情以外的资料（档案、语音、描述），两张表都找，分页；开头写所属对象 |
| `grep(pattern, story_ids?/collection?, context, max_hits, game?)` | 子串匹配，`\|` 表示任一。不给范围：全库按故事统计；给范围：命中行加上下文 |
| `sql(query, game?)` | 一条只读 `SELECT`/`WITH`，200 行，8 秒超时。用来统计和按条件找，不用来翻页读长文 |
| `guide()` | 知识库手册：表与列、绑定、资料页结构、终末地库的结构（`loreLibraryManual`） |
| `outline(collection)` | 故事集的章节、关卡号、官方梗概；末尾是相关的故事集 |
| `similar_names(name)` | 读音或字形相近的名字 |
| `gather(names)` | 按名字取材（§3.2）；模型也可以自己调用 |
| `wiki_search` / `wiki_read` | 开着“Wiki 资料”时才有（`WIKI.md`） |
| `delegate(task, story_ids?, collection?)` | 开着“子助手”时主 agent 才有：新开一个 `LoreAgentLoop`（`subtask: true`，最多 10 轮，每题最多 2 个），交回带出处的要点，看过的行并入主 agent 的 `SeenLines` |

### 4.1 工具输出的规矩（原因都来自真实会话）

- **词的分布与“各给一段”**：`search` 结果开头每个词一行，写它在哪几部故事集里各有多少行（`computeTermSpread`：列到八成或 6 部，补最多 2 部“占比高的”短篇，写出其余的占比）；
  分布里列出、最相关的 5 篇没覆盖的故事集，各给一段原文（`_elsewhere`，每个游戏最多 6 段、共 3500 字）。分布只是定位线索、不算已读；所有词同一个格式。
- **`near`**：给一段读过的剧情的位置，用库里已有的向量找别的故事集里相近 0.70 以上的段落；不调嵌入服务。`query` / `near` 至少给一个。
- **较远的游戏只列一行**：某个游戏最接近的段落比另一游戏远 0.08 以上、关键词命中也不比它多时，只写一行说明和命中数。
- **相关的故事集**（`outline` 末尾）：共有说话人（两边各 10 行以上）与剧情向量的故事集平均方向按名次融合，前 6 个；库里没有数据说明谁承接谁，它只是线索。
- **范围内检索**：`search` 的 `collection` 在关键词与向量候选排名之前生效，避免全库的高分结果挤掉指定故事集的结果。
- **命中的向量块**：按库里实际的起止行读取，不把行号差当成行数。迁移过的块可能包含超过 12 行正文；单片段按字符预算在行之间停止，标出未展示范围，整份结果仍受原有预算限制。
- **“只列出一部分”要说剩下的在哪**：`grep` 截断时列出没列出的命中在哪些故事、各几处。指路模型不照做而工具自己能做的由工具做（`wiki_search` 多词无结果时逐词搜）。
- **0 行如实说**，并对“名字”给近似名提示：库里有完全相同的名字时不提示；类别、id 片段不算名字。
- **凡是“属于谁”的信息按表里的 id 给出**（语音的所属干员、资料的所属对象），不让模型按内容猜。

### 4.2 守门

进入对话的调用参数必须是合法 JSON：粘连的参数拆成几个调用，按工具的 schema 校验（必填、未知参数、数字与数组的读法、`requireOneOf`）。
非法调用不执行，报错写明收到了什么、缺什么、正确写法；模型的原始参数不原样存进历史。某一轮的调用全部被拒时，一旦后面有调用成功，那一轮不再出现在请求里。

### 4.3 没有结果的查找

一个工具在一次问答里没有结果满 6 次（`maxFailedLookups`）之后不再执行；全是空结果的一轮在模型回复过一次之后不留在上下文里（`emptyTurns`），只留次数和试过的调用清单。对所有工具、所有问题一样。

## 5. 出处与答案

### 5.1 出处

- 剧情 `story_id:起始行-结束行`（`line_index`，从 0 起）；资料 `record:<id>`；Wiki `wiki:<站点>:<页面>@<版本>:起始段-结束段`。
- 必须是工具连同正文给模型看过的（`SeenLines`）：`read_story` 的页面、`grep` 的命中与上下文、`search` 与 `gather` 列出的行、资料片段、带 `story_id + line_index + content` 的 `sql` 结果、`read_record` 与 `wiki_read` 展示的内容。新工具一律经它登记。
- 按实际输出逐行登记；被字数预算省略的片段、稀疏行号之间不存在的行都不算已读。`grep` 只在完整行之间截断，附续读位置。
- 标题、分段、步骤、任务、未定位提示、教程、分隔与梗概（`title` / `section` / `step` / `stage` / `unplaced` / `system` / `divider` / `summary`）仍可展示以帮助定位，但不登记为证据。`sql` 会回查原始行的种类，省略 `kind` 列不能绕过限制；查证“没有查到”也遵守同一规则。
- 范围只有一部分读过时，代码裁成读过的那几段；没读过的出处不超过三分之一时由代码删去；只写文件名、而读过的剧情里只有一篇同名时补全路径。
- 多数出处没读过、缺行号、读过资料却一条出处都没有、JSON 提前闭合而后面还有条目读不到——**整轮退回一次**：被退回的答案不进对话、不显示，原因写进会话记录并作为“记录：…”一行出现在工作过程里。
- **代码查的是“看没看过”，不查这些行是否支持那句话。**

### 5.2 答案格式

```
{"verdict": "...",            // 只在核查某个说法时
 "entries": [{"heading": "<小节标题>"},
             {"text": "<正文>", "cite": [["<story_id>", 起始行, 结束行], ["record", "<记录 id>"]]}],
 "coverage": "full|gaps", "gaps": "<可能遗漏的方面>",
 "missing": [{"point": "<没查到的事>", "words": ["<名字>"]}]}
```

- `LoreAnswerStream` 边收边转成 markdown：小节标题前的条目是段落，之后是列表项，出处接在每条末尾；故事集名、章名由代码按目录补出。
- 解析器容错：平铺的 `cite`、`L97` / `97-127`、漏写 `.txt`、`record:record:`；提前闭合的接着读同一个数组；没转义的引号按后文判断；一次回复里有几份答案时取最后一份完整的。丢掉的出处计数并退回一次。
- 条目里的字段顺序不影响显示：`cite` 在 `text` 前时暂存引用，正文结束后再显示，正文仍逐字输出。
- 写给玩家：用自己的话叙述，正文不提库、表、文件名、id；不要大段照搬台词；用提问的语言写。写错的名字由模型按原文写法作答并注明。
- 凡是代码要严格解析的格式，提示词都给完整骨架。

### 5.3 状态信封

not_covered：没有任何核实过的出处（代码定）。partial：模型写了 `"coverage": "gaps"`，或子助手到了轮数上限。answered：其余。
**answered / partial 取决于模型自己有没有声明遗漏，代码不核对，不要拿它的比例当质量指标。**

## 6. 追问、查证与安全阀

### 6.1 追问

`AskChatNotifier` 按回答的消息 id 保存对话、`SeenLines` 和 `ContextLedger`（`LoreConversation`），下一问接着同一段对话；上一问的工具结果原样留着（直到压缩），
追问能直接看到上一问读过的原文。`LoreConversation` 随会话文件保存，重启 App 后打开对话和没关过一样（§6.7）；0.20 之前的旧会话没有它，从答案文本开始。

### 6.2 追问重读（S0）

追问的拟定之前，代码按上一答里引用、且读过的剧情行段调用 `read_story` 重读（`LoreAgentLoop.followUpReads`：前后各两行，相距 20 行以内合成一段，按引用顺序，共最多 400 行）。
这一步同样经过去重：还在上文的行不再读，全部在上文时这一步不出现（0.20 起没压缩过的追问通常就是这样）。
对话里的上一答是 JSON，引用从 `cite` 里取（2026-10-19 之前只认文本写法，真实对话里从没执行过）。

### 6.3 查证“没有查到”

答案通过出处核对后，代码用 `missing` 的名字取材一次（`CoverageBuilder`，约 1.2 万字），只留完全没读过的段落：有就登记为已读、连同原答案交回重写（每问一次，`loreMissingFoundNote`）；
没有就照原样接受，工作过程里记一行“已查证”。它只查模型自己声明的空白。

### 6.4 提要与复核

答案下方的按钮，只对本次运行期间的答案有（条目和对话只在内存里）。
提要（5 条以上条目）：模型只写段落和每段概括的条目号，出处是这些条目出处的并集。复核（只对最后一条）：另一次调用以读者身份、看不到原文，只问故事层面的事，最多三问；有疑问时走同一条流程的追问，原答案不动。

### 6.5 安全阀与兼容

- 主 agent 不限轮数（0.20，开发者 2026-10-25），直到作答、取消或出错；子助手最多 10 轮，最后一轮附“轮数已到、直接作答”的说明，接受 `tool_choice` 的服务商另发 `none`。
- 防空转：连续 3 轮的调用全部因“还在上文”被拦下，下一次请求带 `toolChoice: none` 和“需要的原文都在上文里，请根据上文作答”（对所有问题一样）。
- 旧的“超过 8 万字折叠最早的工具结果”在 0.20 删掉了，换成 §6.6 的压缩。
- 空回复：先原样重试，再改非流式、再改文本协议——只对这一轮；服务商明确拒绝 `tools` 时整题改用文本协议（`` ```tool {…}``` ``）。
- 模型调用没有输出时状态行每 10 秒显示已等待多久；取消立即断开事件流并记下用量（已发出的请求仍在后台跑完，见 `KNOWN_ISSUES.md`）。
- 问答用自己的数据库连接，失效时重开。思考档位每个角色显式指定，默认全部关，“深度思考” = low。

### 6.5 不重复读取（0.20）

两个概念分开记：**已读**（`SeenLines`，这一行的原文在这个对话里展示给模型过，出处核对只认它）和**在上文**（`ContextLedger`，这一行的原文**现在**还在发给模型的对话里）。
被压缩掉的读仍算已读（可以引用），但不算在上文（可以再读）。

- `read_story`：要读的证据行全部在上文 → 不执行，结果写明在第几步、要读后面用 `start=…`；部分在上文 → 执行，略去在上文的那几段并原处注明。
- `read_record`：同一条资料的全文在上文 → 不执行（片段不算）。`wiki_read`：要读的段落全部在上文 → 不执行。
- 任何工具：名字和参数（键排序后的 JSON）都相同、上一次的结果还在上文 → 不执行。
- 被拦的调用不编号、不算“没有结果”，一轮全部被拦时不算一轮；模型发出下一个能执行的调用后，被拦的那对消息从对话里拿掉。工作过程里标“已在上文”。
- 拟定的第一批查找同时开始（并发），展示时仍按顺序。

### 6.6 上下文用量与压缩（0.20）

- **上下文** = 这个对话最近一次主请求的输入 token 数（服务商报的 `promptTokens`；没报时按字符数 / 1.6 估算，界面标 `≈`）。是“模型现在看着多少”，不是累计花费。
- 设置“AI 服务”里两项：**上下文提醒值**（32k–1M，默认 1M）与**自动压缩位置**（提醒值的 50%–90%，默认 80%）。长上下文模型压缩效果常常不好，所以默认值放到最大（开发者 2026-10-26）。
- 每次发请求前估算：`上次的 promptTokens + 之后新加的字符数 / 每 token 字符数`。到了压缩线就先压缩；上次压缩后涨幅不到提醒值的 10% 不再压。追问开始时同样检查。
- 压缩是一次额外的模型调用（同一个 client、同样的 system 与工具定义、`toolChoice: none`，前缀与上一次请求相同），要模型只输出 `{"notes": "要点", "keep": ["出处", …]}`。代码用它**重建对话**：
  一条“对话纪要”消息——问过的每个问题、上一个回答（条目文字加出处，不放 JSON）、`notes`、**保留的原文**（`keep` 里已读的部分，由代码从库里取原文按工具的格式打印，合计不超过 `提醒值 × 0.3 × 1.6` 字，放不下的列出来）、
  已读但不在上文的行段清单（可以引用，要用先重读）、压缩发生在一问中途时的当前问题；中途压缩时后面接最后一轮完整的工具调用与结果，但这一块算进保留原文的预算，超过一半就不原样放（压缩时模型已经看过，要用的写进 keep）。
- 压缩失败（出错、读不出 JSON）：代码自己压——不要点，保留上一答引用过的原文，记一行“压缩没有成功”，**不停止作答**。
- 工作过程里压缩是单独一步“压缩上下文 约 84k → 21k、保留了几段原文”，点开是纪要全文。
- 2026-10-26 真实模型实测（提醒值 64k，三问连续追问）：三次压缩 52k→10k、58k→15k、57k→12k，三个答案前后连贯，第三问接着纪要答得完整。

### 6.7 对话完整保存（0.20）

会话 JSON 的 `lore_conversation`：对话消息（role、content、tool_calls、tool_call_id）、`SeenLines`、`ContextLedger`、压缩次数、最近的上下文 token 数。
打开保存的对话时有它就接着问；正在作答时 App 被杀，保存的是上一问答完时的状态。

## 7. 界面

- **工作过程**（答案上方，默认折叠）：每一步是序号、工具名、模型写的参数原文、结果的计数和字数，加标记（拟定 / 已在上文 / 没有结果 / 出错 / 未执行 / Wiki 超时 / 助手 n）；点开是完整的参数和结果。压缩是单独的一步，点开看纪要。
  代码对答案做的事（退回、裁剪、删去出处、补全路径、查证）是“记录：…”行。不要改回概括句。
- 答案按块显示，出处放在该块下面的证据链里（故事集 → 章 → 行段）；点行号打开原文阅读页并高亮；资料出处打开所属条目的资料页；Wiki 出处弹出快照。
- 问答列表不跟随流式内容滚动；思考窗口固定高度；阅读位置上方的内容在流式中不变高。
- 输入框上沿显示最近一次主 agent 请求的上下文 token 数及提醒值；服务商没有报告时按全部消息字符数 / 1.6 估算，数字前标 `≈`。上下文写入本问用量，答案下显示 `ctx`。提醒值在设置“AI 服务”中调整，默认 1M；达到时显示强调色提示，每次上升越过提醒值弹一次窗，后台对话切回时再弹。修改提醒值只更新显示，不触发弹窗。
- 输入框（0.20）：没有焦点时是一行（选项、草稿第一行、发送），点哪里都弹键盘、变成两行（文字在上，选项 / 展开 / 发送在下，按钮之间的空白也能点）；可以展开到半屏、全屏；**回车一律换行**，只用发送按钮发；失去焦点或发出问题后回到一行，草稿保留。
- 选项按钮的面板不取焦点（键盘不动）：Wiki 资料 / 子助手 / 深度思考（服务商有思考开关时才有）。
- 答案里有立绘的人物名字保持正文色，带 2 px 强调色下划线；点名字先显示旁边的小卡片，点“更多”打开立绘卡片（`PORTRAITS.md` §4；设置里可以让干员名不标）。
- 没有向量服务时提示“只用关键词检索，问答质量会显著下降”。

## 8. 关于数据的两点（提示词里的约定）

- `start_time`（活动、目录）是**上线时间**；`show_time` 是剧情回顾开放时间，也不能直接视为首次上线时间。两者都不是故事内时间；后上线的内容可以补充或推翻先上线的叙述。游戏数据里没有故事内的时间表，提示词要求从原文判断先后，不按上线顺序推断。
  取材按上线顺序排列只是为了好读。
- 同一干员的不同版本来自 `char_meta_table.spCharGroups`（`same_person` 链接，异格 → 原型）；“同一人物后来的经历”与“假设线”表里不区分，由模型读档案与剧情判断。
