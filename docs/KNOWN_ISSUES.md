### 1.2 检索

| 问题 | 现状与方向 |
| --- | --- |
| 没有中文全文索引 | FTS5 `unicode61` 不分中文词（0.14 已删）；原文检索用 LIKE 全表扫描，44 万行。原来手机每库 1.3–6.3 秒：每次检索扫两遍（先数各词的行数、再排名），装了两个游戏时两个库一个等一个（终末地库小得多耗时却接近，就是在排队）。2026-11-14 起只扫一遍（命中行带每个词一位的标记进临时表，数行数和排名都读它），两个库同时查，`grep`、资料检索、按名字取材同样并行；真实库上结果逐条相同，桌面每次检索 0.55–1.6 秒 → 0.25–0.43 秒。手机上的新耗时没量。trigram 全文索引在手机的 SQLite 上是否可用没验证 |
| 没有组织/概念级的汇总 | 组织、地点、概念没有可枚举的表，只能从文本涌现；不建人工词典 |
| 没有向量服务时只有字面检索 | 检索词由模型写；界面提示“问答质量会显著下降” |
| 向量服务偶尔出错 | 那一题退回关键词检索并提示，不重试（40 次运行里 2 次） |
| 略去较远的游戏用的是固定差值 0.08 | 问题的词两边都常见、答案其实在较远的那个游戏里时会被略去，靠那一行提示再查 |

## 2. 问答

### 2.1 质量（没有解决）

现象、试过的办法和数据见 `ASK_EXPERIMENTS.md` §0 与 §5。摘要：

| 问题 | 现状 |
| --- | --- |
| 概念题找不到原文 | 金标是顺带的一两句台词；第一步能给到的金标行最多 74–79%；场景卡、检索块前缀都没解决 |
| 取材后“够了就答” | 第一步给了 3 万字，模型常常一次工具都不调用就作答；查证“没有查到”只在模型自己声明空白时起作用 |
| 答案的先后顺序 | 活动当主线、先后写错；2026-10-24 用补全目录时间的库复验仍失败，还把计划写成已发生、把缺少前文的潜意识画面写成真实经历。目录时间不能解决这些阅读错误。2026-11-14 同题（塔露拉）复测一次：先后正确，没有这些错误（`ASK_EXPERIMENTS.md` §12），一次不能说明已解决 |
| 拟定的第一批查找带进无关的词 | 约三分之一的题：很泛的名字、资料种类的词、不相干的人物；玩家没提 Wiki 时也写 `wiki_search` |
| 锚点不一定是原文写法 | “切尔诺贝利”“龙门贫民区”这类锚点找不到行；起作用的主要是人名 |
| 取材加长了上下文 | 第一轮 prompt 多 5–15 万 token |
| 集成战略的结局与主线混着讲 | 有的答案写明“一条结局线”，有的当成已经发生的事 |

### 2.2 正确性

| 问题 | 现状 |
| --- | --- |
| 出处只核对“看没看过” | 代码查所引的原文行是否展示过，不查这些行是否支持那句话。2026-10-24 真实复验仍有错归说话人、局部言行概括成全国制度；加通用提示未解决。删去无效出处后，对应正文也可能继续保留。独立出处审查能发现部分问题，但附近原文本身不足时仍会漏检；未加入主流程。2026-11-12 起答案格式要求作答前自查（出处是否讲了这件事、是原文、人物说法、梗概还是推断）；2026-11-14 两道题各实测一次，没有发现错归说话人，有一句无出处的“玩家的猜测”（`ASK_EXPERIMENTS.md` §12） |
| 官方梗概可以引用（2026-11-12） | 可能让“够了就答”更明显：读完梗概就作答、不读原文。2026-11-14 两次实测都读了原文、没有引用梗概；要更多样本才能下结论 |
| 跨游戏推理 | “佩丽卡 幕后高层”一题 6 个会话全部 partial 或取消：明日方舟库几乎不查、先定社区的猜测再找证据。2026-11-14 “零号委托的创始人”一题实测一次：专门查了明日方舟库并引用，候选写成带依据的推断，answered（131 万输入，偏贵）。方向仍只能是通用机制，不写人物分支 |
| 人物的话与推断（0.21） | 提示词要求人物的话不直接当事实、原文没明说时作出推断并标明。2026-11-14 两次实测都下了判断、标明了推断，事实与推断没有混写（`ASK_EXPERIMENTS.md` §12） |
| 深度思考时输出上限被思考吃掉 | 2026-11-14 实测作答轮两次被 8192 截断；现在被截断的一轮放宽到 16384、32768 重试，只有离线测试 |
| 核查结论要模型自己写 | “有人说……对吗？”被当成普通问答时没有核查标记；按 R13 不由代码判断题型 |
| 英文提问用中文作答 | 历史问题集里唯一的英文题两次都是；提示词里已有“用提问的语言写” |

### 2.3 成本、耗时与工程

| 问题 | 现状 |
| --- | --- |
| 耗时 | GLM 一题约 1–4 分钟（带工具的调用有 4.5–8 秒底噪） |
| 库里没有的内容要找很久才放弃 | 一题 41 步、98.8 万输入；没有结果的查找的上限按工具分别计数（每个工具一问 6 次），换着工具查仍可以查很久 |
| 长整理题很贵 | 二十多次 `grep`、27–55 万输入 |
| 总是返回空回复的服务商每轮多两次请求 | 空回复先原样重试、再降级，只对这一轮 |
| “提要”“复核”只在最后一个答案下 | 会话文件只存最后一问的对话（2026-11-14 起恢复的会话也有这两个按钮）；更早的答案要提要或复核，先在下面追问 |
| 上下文压缩（0.20） | 2026-10-26 提醒值 64k 下真实模型测过三问：压缩后 10–15k，答案连贯。提醒值低时，追问一开始取材就越线，每问开头都会压缩一次，之前读过的原文多半只剩纪要里的摘录。2026-11-14 再测（`docs/ASK_EXPERIMENTS.md` §12.1）：提醒值 20 万、12 万下两三问都没到压缩线（最大一次请求 15 万）；6 万下压缩两次，压缩后答案连贯，第一次纪要被 4096 的输出上限截断（深度思考），已改成与作答同一上限、截断时放宽重试。默认 1M（压缩线 80 万）在一般对话里几乎不会触发，真正到 80 万时的效果没测；长上下文模型压缩效果常常不好，这也是默认值放到最大的原因 |
| 不限轮数（0.20） | 主 agent 一直查到作答、取消或出错；防空转只有“连续 3 轮全部被拦就要求作答”和“没有结果的查找每个工具 6 次”。库里没有的内容可能查很久 |
| 免费的 glm-4.7-flash 测不了 | 并发数 1、服务端常过载（429、300 秒无输出）；测试用 glm-5.3-flash（`LLM_PROVIDERS.md`） |
