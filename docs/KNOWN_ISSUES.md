## 1. 知识库

### 1.1 重建的知识库（2026-10-19 重建，2026-10-20 发布到 `gamedata-20261020`）

两个库都按现在的建库代码重建过，向量全部从旧库迁移（新算 0 块），逐表与 v0.14.0 的资产对比过：

| 库 | 位置 | 与 v0.14.0 资产的差别 |
| --- | --- | --- |
| 明日方舟 | `build/gamedata_rebuild/`（上游 `17759cc`，与 v0.14.0 同一份游戏数据） | `story_catalog` 多一列 `show_time`（剧情回顾的开放时间，2032 篇里 1638 篇有值，主线 429 篇全部有）；其余表只有 `updated_at` 时间戳不同 |
| 终末地 | `build/endfield/`（旧库备份在 `build/endfield_v0140/`） | 33 份干员档案的 id 加了 `ef/`（`entity_documents` 与对应的 452 块资料向量）；`story_catalog` 多一列 `show_time`（终末地全为空）；其余只有时间戳 |

- `show_time` 是分支 `ask-recall-eval` 的改动（按名字取材按上线顺序排，主线只有这个时间），不是 0.14.5 的；档案 id 是 0.14.5 的改动（`923f476`）。
- 发布（2026-10-20）：两个 gz 与 manifest 先上传到 `gamedata-20261020`（只发知识库的 Release，不标 latest），同日随 v0.15.0 再传一份（同样的文件、同样的 SHA），
  公开地址下载后 SHA 一致；`release_gamedata.env` 与 `gamedata-channel` 上的渠道文件指向 v0.15.0（`min_app_build` 仍是 33）。
- 安装器的校验从 v0.14.0 起没改过（只查必需的表、schema 版本和计数），v0.14.x 的 App 装得上新库，只是不读 `show_time`（只有本分支的取材用它）。
  已做的检查：明日方舟库的真实库验收（`gamedata_v5_acceptance_test.dart`）、终末地库的验收（`endfield_acceptance_test.dart`，含安装器校验）都通过。
- 对 v0.14.5 的用户：渠道文件里的资产与包里的同一提交、同一日期，按规则视为“不比包里的旧”，所以装着 v0.14.0 官方库的手机会提示更新、重新下载两个库
  （明日方舟约 119 MB，换来的 `show_time` v0.14.5 不用；终末地的档案 id 修正对它有用）。真机上没有试过这个提示与安装。v0.14.0 的 App 不读渠道文件，不受影响。
- **终末地库换成了 2026-10-18 的客户端**（2026-10-20，开发者同意直接覆盖）：v0.15.0 Release 上的 `arklores_endfield_zh.db.gz` 与 `endfield_manifest.json` 已替换
  （SHA `53b935b2…`，`gamedata-20261020` 上的仍是旧的 `77b69d3a…`），渠道文件同步改了。新增第二章进程VIII“离渊”（5 个任务）、干员“祀”（干员任务、Baker 话题、帝江号互动）、
  武陵的支线/探索/活动任务与两个调查档案，剧情行 49121 → 53088、资料 3251 → 3611，没有删掉的故事；向量按行迁移 9814 块、新算 1123 块。
  **v0.15.0 的 APK 里烘的是旧 SHA**：App 靠渠道文件拿到新 SHA，读不到渠道文件时下载终末地库会校验失败（重试即可）。真机没试过。
  旧库备份在 `build/endfield_v0150/`。

### 1.2 检索

| 问题 | 现状与方向 |
| --- | --- |
| 没有中文全文索引 | FTS5 `unicode61` 不分中文词（0.14 已删）；原文检索用 LIKE 全表扫描，44 万行：桌面 <1 秒，手机每库 1.3–6.3 秒，是检索耗时的大头。终末地库小得多耗时却接近，像是在同一连接上排队，没有查代码确认（入口 `SearchTool._rank` → `searchStoryLinesLike`）。trigram 全文索引在手机的 SQLite 上是否可用没验证 |
| 没有组织/概念级的汇总 | 组织、地点、概念没有可枚举的表，只能从文本涌现；不建人工词典 |
| 没有向量服务时只有字面检索 | 检索词由模型写；界面提示“问答质量可能下降” |
| 向量服务偶尔出错 | 那一题退回关键词检索并提示，不重试（40 次运行里 2 次） |
| 略去较远的游戏用的是固定差值 0.08 | 问题的词两边都常见、答案其实在较远的那个游戏里时会被略去，靠那一行提示再查 |

## 2. 问答

### 2.1 质量（没有解决）

现象、试过的办法和数据见 `ASK_EXPERIMENTS.md` §0 与 §5。摘要：

| 问题 | 现状 |
| --- | --- |
| 概念题找不到原文 | 金标是顺带的一两句台词；第一步能给到的金标行最多 74–79%；场景卡、检索块前缀都没解决 |
| 取材后“够了就答” | 第一步给了 3 万字，模型常常一次工具都不调用就作答；查证“没有查到”只在模型自己声明空白时起作用 |
| 答案的先后顺序 | 活动当主线、先后写错；重建的库补了主线的时间（§1.1），没有用真实模型复验 |
| 拟定的第一批查找带进无关的词 | 约三分之一的题：很泛的名字、资料种类的词、不相干的人物；玩家没提 Wiki 时也写 `wiki_search` |
| 锚点不一定是原文写法 | “切尔诺贝利”“龙门贫民区”这类锚点找不到行；起作用的主要是人名 |
| 取材加长了上下文 | 第一轮 prompt 多 5–15 万 token |
| 集成战略的结局与主线混着讲 | 有的答案写明“一条结局线”，有的当成已经发生的事 |

### 2.2 正确性

| 问题 | 现状 |
| --- | --- |
| 出处只核对“看没看过” | 代码查所引的行是否展示过，不查这些行是否支持那句话：所引的故事里没有被解释的那个词、把一个人的话引到另一个人身上、直接接受提问里的前提。靠“复核”按钮或读者点开出处 |
| 跨游戏推理 | “佩丽卡 幕后高层”一题 6 个会话全部 partial 或取消：明日方舟库几乎不查、先定社区的猜测再找证据。方向只能是通用机制（工具给出实体在另一游戏的条目、规划时允许一条另一游戏的概念查找），不写人物分支 |
| 核查结论要模型自己写 | “有人说……对吗？”被当成普通问答时没有核查标记；按 R13 不由代码判断题型 |
| 英文提问用中文作答 | 历史问题集里唯一的英文题两次都是；提示词里已有“用提问的语言写” |
| 较弱的模型一次回复里写多份答案 | 解析取最后一份完整的；流式时用户先看到第一份 |

### 2.3 成本、耗时与工程

| 问题 | 现状 |
| --- | --- |
| 耗时 | GLM 一题约 1–4 分钟（带工具的调用有 4.5–8 秒底噪） |
| 库里没有的内容要找很久才放弃 | 一题 41 步、98.8 万输入；没有结果的查找的上限只管同一个工具连续落空 |
| 长整理题很贵 | 二十多次 `grep`、27–55 万输入 |
| 取消后在途请求不中断 | 事件流立即断开、用量当场记下，但已发出的 HTTP 请求在后台跑完，其用量可能记到下一问。`chatCompletion` 已有 `abortTrigger`（拟定那次用了），流式请求和取消还没接上 |
| 问答进行中保存设置可能中断问答 | 设置变化会重建 client provider；方向：有进行中的问答时延后生效 |
| 总是返回空回复的服务商每轮多两次请求 | 空回复先原样重试、再降级，只对这一轮 |
| “提要”“复核”只对本次运行期间的答案有 | 条目和对话只在内存里；恢复的会话没有按钮 |
| 免费的 glm-4.7-flash 测不了 | 并发数 1、服务端常过载（429、300 秒无输出）；测试用 glm-5.3-flash（`LLM_PROVIDERS.md`） |

## 4. 界面

| 问题 | 现状 |
| --- | --- |
| 悬浮 UI 不会自动隐藏 | `FloatingBar` / `FloatingScaffold` 常驻。待定方案：A 单击唤起、翻页或静止约 3 秒收回（与选字冲突）；B 上下滑收起、停止后展开（发现性差）；C 只在顶部或底部边缘热区唤起（误触最少）。WebView 收起时要同步改网页内边距。开发者打算在 UI 重构时一起做 |
| Wiki 悬浮栏 | 网页铺满，靠注入的留白与平移站点自己的 fixed/sticky 栏；个别站点可能仍被遮住，要逐站确认 |
| 阅读页没有滚动条 | 惰性列表从锚点双向建，总高度靠滚动校准；这是“任意长的故事打开不卡”的代价 |
| 条目类型、分组、绑定名只有中文 | 游戏内容用语，与库内容同语言；模型的错误信息中英混杂 |

## 5. 终末地知识库

| 问题 | 现状 |
| --- | --- |
| 只能在电脑上从游戏客户端重建 | 没有可增量跟随的社区仓库；App 里只能下载发布的库（缺向量时可在 App 里补） |
| 一个任务里不同种类的对话谁先谁后不知道 | 对话、通讯、远程通话、闲话各自编号；按种类分块、块内按编号，提示词告诉 Agent 不要跨种类推断先后 |
| 少数台词按行号排 | 约 11% 的台词行既不在对话树里也不在时间线里；一段对话有几条时间线时（14 段）台词混排在第一个过场处；按选项分支的时间线片段没有展开 |
| 主角台词只收女性版本 | `{F}…{M}…` 只留一种（kit 的默认） |
| 未实装任务里有 7 个无名的 | 叫“无名任务（<任务 id>）”，只在“未实装任务”书架上 |
| 不收的 | 档案、语音的解锁条件（玩法）；干员简介（不在客户端的表里，应是官网文案） |
| 数据本身的缺口 | 势力表为空（势力名改从干员的阵营标签取）；闲话多半没有说话人；部分来信看不出寄信人 |

## 6. Wiki

| 问题 | 现状 |
| --- | --- |

## 7. 工程

| 问题 | 现状 |
| --- | --- |
| 没有 App 更新提示 | App 里没有检查新版本的功能；渠道文件只管知识库。方向：读 GitHub 最新 Release 的版本号，比本机新就在设置里提示 |
| 死代码 | `lib/core/rag/chunker.dart` 没有任何代码引用 |
| 长文件 | `lore_agent_loop.dart`（1800 行）、`chat_bubble.dart`、`story_reader_page.dart`、`wiki_browser_page.dart`、`arknights_importer.dart` 各是一个整体 |
| 测试 | 全量测试在高负载时有偶发超时（写入多的用例超过 30 秒，单独跑通过）；`test/live/scratch/` 下的本地探针（不提交）有的已编译不过，全量测试里会报一个加载失败 |
| 覆盖偏低 | 设置页、知识库页的界面分支；WebView、前台服务、启动图标切换只能真机检查 |
| 没有自动截图对比 | 有溢出断言和布局截图（`ARKLORES_SHOT_DIR`），没有 golden 基线 |
| 真机性能未量化 | 只有桌面计时；冷启动、内存峰值、安装耗时没有记录 |
| 真机问答只能经桥测试 | 带桥的包与发布的包只差这一层；发布的包仍要手动看一遍 |
| iOS 未验证 | 工程还在（`ios/`），0.10 起只在 Android 上开发和测试 |
| 签名 keystore 只有维护者一份备份 | 丢失后无法再发可覆盖安装的版本 |

## 8. 范围

- 明日方舟与终末地是两个独立的库；跨游戏只在检索面合并，不建跨游戏的关系。
- 开发者的项目目标里还有：用终末地风格重构 UI、把《大地巡旅》作为用户资料并定资料可信度（原文 = Wiki > 用户资料）。都没有开始。
