# v0.11 计划：资料页（阅读器 + 用户资料）

> 立项：2026-10-04。0.10 线已收尾（正式版 v0.10.0）。本文是 0.11 的范围、设计、里程碑和已定的决定；开工前先读。
> 角色扮演不在 0.11 范围内（冻结），理由见 `ROLEPLAY_ZOOT_ANALYSIS.md`。

## 1. 目标与范围

把底部导航里一直“暂停”的**资料页**做成真正的页面：

1. **官方内容的离线阅读器（只读）**：用知识库里已有的文字整理出可浏览、可阅读的目录——主线、活动、干员密录、肉鸽剧情、
   教程/沙盘等其他剧情；干员档案与语音、敌人档案、道具/皮肤/勋章描述、关卡与区域描述、肉鸽主题文本等。
   起因：做证据链时发现“点行号打开原文”很有用，整理好后可以脱离问答直接当阅读器用，并且和问答是同一个阅读器。
2. **阅读历史与定位**：继续阅读、最近阅读、书签（行范围 + 笔记），从证据链打开的也记入历史。
3. **用户资料（可增删改）**：导入自己的文本；搜索、阅读、编辑、删除；在用户明确附上时作为 AI 的低可信补充材料。
4. **资料页的统一管理**：一个搜索框覆盖官方内容和用户资料；历史/书签/资料的管理。
5. **知识库跟随解包更新**：官方库只读、整体替换；能看到“上游有新数据”，用增量更新跟上；用户数据不受影响。

**不做**：角色扮演重构、终末地数据、云同步/账号、PDF/网页导入（M4 之后再评估）、CI 定时滚动发布知识库（见 §6）。

目录必须有不依赖 catalog 的**退化分组**（按 `story_scopes` 的范围和源路径），不能为个别活动写名字表。

**档案/记录**：

- 拼好的文档只有干员档案（`entity_documents`，839 份，`operator_profile_bundle`）。
- 其余都是 `normalized_records` 里的条目（共 9.7 万）。最多的几类：
  - 干员语音 18089（431 名干员）
  - 肉鸽主题文本 15978（6 个主题）
  - 关卡描述 8351
  - 敌人档案 7052（1732 个敌人）
  - 道具 5916、皮肤 5676、勋章 4850
  - 沙盘道具 4590、模组 1794、区域 429
- 阅读器需要把同一实体的多条记录**按实体拼成一页**。

**代码**：

- 阅读器 `story_reader_page.dart`：读单个剧情文本、高亮引用行，只能从证据链进入。
- 资料页 `materials_page.dart`：只有一张“暂停”卡片。
- App 里没有用户数据库；Wiki 书签另有一个独立的 sqflite 文件。
- 知识库常规读取全部是 `readOnly: true`；唯一会写库文件的是 v0.10.7 的 `_ensureStoryLinesIndex`。

**更新**：两条通道。

- **release 整包**：首次安装、带向量。
- **App 内构建**：GitHub compare API 分页拿变更文件，逐文件增量导入；在临时副本上构建，校验后原子替换。
  改动故事的向量会作废，其他保留。

上游从 `6844859` 到 2026-10-04 又更新了 **4 次**（最新 `a550f5e`，2026-09-29），大约一周一次。
每次只改 **2–4 个剧情文件和 10–24 个 excel 表**，与 185 MB 的整包相比，增量更新是跟上解包的正路。

## 3. 设计

### 3.1 两个库，职责分开（硬性要求，M1 已落地）

| | 官方库 `gamedata`（现有） | 用户库 `userdata`（新增） |
| --- | --- | --- |
| 内容 | 官方文本、索引、目录 | 阅读历史、书签、用户资料、标签 |
| 读写 | **只读**，只能整体替换（更新） | 可增删改 |
| 更新 | 随解包更新，原子替换 | 随 App 迁移（`PRAGMA user_version`，`userDataMigrations` 只追加） |
| 位置 | 原位置（Android 外部存储目录） | `<documents>/userdata/arklores_user.db`（不同目录） |
| 代码 | `GameDataKnowledgeStore` | `lib/core/userdata/`：`UserDataStore`、`LibraryRef`、`userDataStoreProvider` |

- 两个库互不 `ATTACH`、没有外键。用户数据用**稳定引用** `LibraryRef` 指向官方内容，序列化为 `<kind>:<id>`：
  - `story:<story_id>`
  - `record:<normalized_records.id>`
  - `document:<entity_id>/<document_type>`
  - `user:<id>`
- 官方库更新后，目标消失或改名的引用仍能解析；界面显示“原文已不在当前知识库”，不报错、不删用户数据。
  旧版本 App 遇到新种类的引用就跳过。
- 官方库的更新（整包、增量）绝不碰 `userdata/`。
- **`_ensureStoryLinesIndex` 定为唯一允许的官方库维护写入**：只建一个索引、不改内容、幂等，v0.10.7 起的构建自带。
  不再新增任何就地写官方库的逻辑；需要的新索引/新表一律进构建产物。等所有资产都 ≥ v0.10.7 构建后再删除它。
- 导出/备份：M4 做“导出为 JSON + 文本”，不做云同步。

### 3.2 阅读目录（导航，不是证据）

```
资料
├─ 剧情   主线 / 活动 / 干员密录 / 肉鸽 / 其他（教程、沙盘…）   → 故事集 → 章节（行动前/后）
├─ 档案   干员（档案、语音、模组）/ 敌人 / 道具·皮肤·勋章 / 关卡·区域 / 肉鸽主题 / 沙盘
├─ 我的资料
└─ 历史与书签
```

- **数据面：官方库加一张可选表 `library_index`**（与 `story_catalog` 同性质：缺表时 App 照常工作，目录退化为现场查询）：
  - 列：`ref`（`LibraryRef` 字符串，主键）、`section`（剧情/档案）、`group_path`（如 `剧情/活动/<故事集>`）、`title`、
    `subtitle`、`sort_key`、`start_time`、`item_count`（行数或条目数）、`char_count`。
  - 构建时由现有源字段**确定性**算出：剧情来自 `story_catalog` + `story_scopes`（没有目录的退化为按范围 + 路径），
    档案来自 `entity_documents` + `normalized_records` 按 `entity_id` × `content_type` 分组。两次构建结果一致（检索原则 4）。
  - 预计算的目的：手机上打开目录时不对 41 万行做 `GROUP BY`。
  - 全量构建、App 内增量构建、`tools/` 补表工具都维护它（与 story_catalog 相同的三处）。
- **分组规则对任意活动/任意故事集成立**，不为某个活动写名字或顺序（遵守 `CLAUDE.md` 的检索原则和禁止特判）。
- **两种阅读器**：
  - **剧情阅读器**：行流，从现有 `StoryReaderPage` 扩展出无高亮打开、上一章/下一章、章内搜索、记住位置。
  - **文档阅读器**：同一实体的记录按小节排版。
  - 两者共用样式，也共用“带位置打开”的入口 `LibraryTarget(ref, line?)`；证据链、搜索结果、历史、书签都从它进入。
- **搜索**：官方内容先复用 `story_lines_fts` / `entity_documents_fts`（trigram）+ LIKE 回退。`story_lines_fts` 用的 unicode61
  对中文基本无效（已知债务），M3 测量后决定是否在构建产物里加 trigram 索引（体积代价要量化，比如 +100 MB 就不做）。
  用户资料用自己的 FTS5（用户库走 FFI 自带的 SQLite，保证 trigram 可用）。

### 3.3 历史与定位（M1 数据层已完成）

- `reading_progress`（每个 ref 一行）：
  - 字段：标题、行号、打开时间、次数、读完、是否只从证据链打开过。
  - 从证据链打开**不会覆盖**资料页里的阅读位置；“只从证据链打开过”的条目可以从“继续阅读”里过滤掉。
- `bookmarks`：ref、行范围、笔记、时间。
- 定位：按行号滚动并高亮（沿用现有机制）。位置写入节流，例如停止滚动 1 秒后写。

### 3.4 用户资料（M4）

- **导入**：txt / md，文件选择器；大文件沿用 `rag/chunker.dart` 分块，只用于搜索和附上。
- **管理**：新增、重命名、编辑正文、删除（需确认，用户库内真删除）、标签、搜索（FTS5）、按时间排序。
- **与 AI 的关系**：用户资料是**低可信来源**。
  - 默认不参与问答。只有用户在问答页明确“附上”某份资料时，它才作为“用户提供的文本”放进上下文，做法与现有的 Wiki 转交相同。
  - 官方出处仍只来自知识库（`SeenLines` 不变），用户资料的引用用不同的标记显示，不进官方证据链。
  - 不新增“替模型决定信哪个”的规则。
- **隐私**：用户库只在本机；会话日志只记录引用了哪份资料，不复制资料正文。

### 3.5 知识库跟随解包更新（M5）

1. **更新检查**：
   - 知识库页显示已装库对应的上游提交和日期，以及“上游有 N 次更新 / M 个相关文件变化”。
   - 用 compare API，结果缓存一天；没配 token 时按 GitHub 匿名限额（每小时 60 次）处理。
   - release 通道继续用 `.asset_sha256` 判断。
2. **App 内增量更新作为常规通道**：
   - 后台服务保活（v0.10.6 已有），可取消，失败保留旧库，校验后原子替换。
   - 补上 `library_index` 的增量维护。
   - 更新后给出**差异报告**：新增/改动了哪些故事集、章节、档案，并直接链到资料页。“这次更新了什么”本身就是一份阅读入口。
3. **整包**：仍用于首次安装和向量；数据发版时照常更新 `tools/release_gamedata.env`。
4. **向量**：增量更新后，改动过的章节没有向量（`find` 对它们退化为关键词检索），状态里要说明；重新生成向量需要 embedding key，
   只在整包发版时做。

## 5. 不变的约束

- 官方库只读；用户数据只进用户库；引用用稳定标识。
- 目录、搜索、历史、书签都是**导航，不是证据**；证据只来自 Agent 读到并通过 `SeenLines` 核对的原文。
- 不为具体剧情/人物/活动写分支、名字表或顺序表；目录规则对任意故事集成立。
- 长时操作（导入大文件、更新知识库）包在 `BackgroundWork.instance.run(...)` 里。
- 本阶段基本不需要真实 API；需要时仍遵守成本约束。

## 6. 已定的决定（开发者可改）

1. 角色扮演冻结，0.12 不预排重构（`ROLEPLAY_ZOOT_ANALYSIS.md`）。
2. 不做 CI 定时滚动发布知识库：要仓库 secrets，还要 embedding key（花钱）；App 内增量更新已经能跟上每周的解包。
3. 用户资料先支持 txt / md。
4. 阅读器随 M2 加字号设置，其余跟随 App 主题。
5. 角色扮演页是否从界面移除，等资料页稳定后由开发者决定。
