# v0.11 计划：资料页（阅读器 + 用户资料）

> 立项日期：2026-10-04。0.10 线已收尾（正式版 v0.10.0）。本文是 0.11 的范围、设计和里程碑，开工前先读。
> 角色扮演不在 0.11 范围内，理由见 `ROLEPLAY_ZOOT_ANALYSIS.md`。

## 1. 目标

把底部导航里一直处于“暂停”状态的**资料页**做成真正的页面，它有两个来源：

1. **官方资料（只读）**：用知识库里已有的文字整理出可以**离线阅读**的内容——关卡剧情、活动剧情、主线、
   干员密录、肉鸽剧情，以及干员档案、语音、敌人档案、道具/皮肤/勋章描述、关卡描述、世界观文本等。
   起因：做证据链时发现“点行号打开原文”这件事很有用，整理好之后可以脱离问答直接当阅读器用。
2. **用户资料（可增删改）**：用户导入自己的文本，用来搜索、阅读，并在用户明确选择时作为 AI 的补充材料（低可信来源）。

再加上**阅读历史与定位**、全文搜索、管理，以及**知识库跟上游解包更新**的可靠路径。

不做：角色扮演重构、终末地数据、云同步、账号。

## 2. 现状（已核对代码和真实库）

- 知识库 `arklores_gamedata_zh.db`（schema 4，约 560 MB 解压，release 资产 185 MB gz）。常规打开都是 `readOnly: true`
  （`GameDataKnowledgeStore._open`），只读 SQL 另有独立的只读连接。**唯一的例外**：v0.10.7 的
  `_ensureStoryLinesIndex` 会在旧库上补建一个索引（写库文件）。
- 内容规模：2816 个剧情文本（41 万行）；记录按 `content_type` 分：operator_voice 1.8 万、roguelike_topic 1.6 万、
  activity_story 8.8 千、stage_description 8.4 千、enemy_profile 7 千、item_description 5.9 千、skin 5.7 千、medal 4.9 千、
  operator_record_story 3.3 千、main_story 2.4 千、roguelike_story 386 等；`entity_documents` 839 篇（干员档案等）。
  `story_catalog`（R14，可选）提供故事集 → 章节的层级、顺序、上线时间和官方梗概。
- 阅读器：`story_reader_page.dart`（单个剧情文本，按行滚动、高亮引用行），只能从证据链进入；没有目录入口、没有历史、
  没有档案类文档的阅读页。
- 资料页：`materials_page.dart` 只有一张“暂停”卡片；没有用户数据库。App 里除知识库外只有 Wiki 书签用 sqflite。
- 更新：两条通道——release 整包（全量下载）和 App 内构建（源仓库按文件增量、后台 isolate、校验后原子替换，
  但不含向量表）。

## 3. 设计

### 3.1 两个库，职责分开（硬性要求）

| | 官方库 `gamedata`（现有） | 用户库 `userdata`（新增） |
| --- | --- | --- |
| 内容 | 官方文本、索引、目录 | 用户资料、阅读历史、书签、标签、笔记 |
| 读写 | **只读**，只能整体替换（更新） | 可增删改 |
| 更新 | 随解包更新，整个文件原子替换 | 随 App 迁移（`PRAGMA user_version`） |
| 位置 | `gamedata/` | `userdata/arklores_user.db`（与 gamedata 分目录） |

- 用户库与官方库互不 `ATTACH`，也不用外键：用户数据通过**稳定标识**引用官方内容（`story_id`、`entity_id`、`source_path`、
  行号），官方库更新后目标消失或改名时，引用降级为“原文已不在当前知识库”，不报错、不丢用户数据。
- 官方库更新（整包、App 内增量）绝不碰 `userdata`。
- 把 `_ensureStoryLinesIndex` 这种“就地修改官方库”的做法收口：新增索引一律放进构建产物；已装旧库的补索引改为
  “提示更新”，或明确标成唯一允许的维护迁移并记在文档里（M1 决定）。
- 用户库的备份/导出：先做“导出为 JSON/文本”，不做云同步。

### 3.2 阅读目录（`library`）——只是导航，不是证据

把现有数据整理成可浏览的树，**不引入任何针对具体剧情的特判**（遵守“检索与数据设计原则”和“禁止特判”）：

```
资料
├─ 剧情      主线 / 活动 / 干员密录 / 肉鸽 / 其他(沙盘、教程)   → 故事集 → 章节（按 story_catalog 的顺序与上线时间）
├─ 档案      干员档案 / 干员语音 / 敌人 / 道具·皮肤·勋章 / 关卡与区域描述 / 世界观文本
├─ 我的资料  用户导入的文本
└─ 历史      最近阅读、继续阅读、书签
```

- 数据面：给官方库加一张**可选**的 `library_index`（与 `story_catalog` 同一性质：缺表时 App 照常工作，目录退化为由
  `story_catalog` / `entities` 推出的列表）：`item_id`（稳定）、`kind`（story / document）、`group_path`、`title`、
  `sort_key`、`start_time`、`ref`（story_id，或 entity_id + document_type）、`char_count`。由构建器从现有源字段确定性算出，
  两次构建结果一致（检索原则 4）。
- 两种阅读器：**剧情阅读器**（行流，复用 `StoryReaderPage`）与**文档阅读器**（档案/描述按小节排版）。同一套样式，
  同一个“带位置打开”的入口（`LibraryTarget(ref, line?)`），证据链、搜索结果、历史、书签都用它打开。
- 搜索：官方内容先用已有的 `story_lines_fts` + LIKE 回退；注意 unicode61 对中文基本无效（已知债务，见
  `KNOWN_LIMITATIONS_AND_DEBT.md`），M2 起测量后决定是否改 trigram/分词。用户资料用自己的 FTS5 表。

### 3.3 历史与定位

`reading_progress(item_ref PRIMARY KEY, line_index, scroll_fraction, opened_at, finished)`，另有 `bookmarks(id, item_ref,
line_start, line_end, note, created_at)`。进入阅读器、离开时写入（节流）；“继续阅读”列表按 `opened_at`；
从证据链点开也记入历史（带 `from_citation` 标记，不算“读过”）。定位 = 按行号滚动并高亮（现有机制）。

### 3.4 用户资料

- 导入：纯文本 / Markdown（先做），文件选择器；大文件分块（沿用 `rag/` 的分块工具）。后续再评估 PDF / 网页。
- 管理：新增、重命名、编辑正文、删除、标签、搜索（FTS5）、按时间排序；删除是用户库内的真删除，需确认。
- 与 AI 的关系：用户资料是**低可信来源**。默认不参与问答；用户在问答页明确附上某份资料时，才作为“用户提供的文本”
  放进上下文（Wiki 转交已是同样的做法），回答里的官方出处仍只来自知识库（`SeenLines` 机制不变），用户资料的引用要
  显示成不同的标记，不进入官方证据链。不新增“替模型决定信哪个”的规则。
- 隐私：用户库只在本机；日志/会话文件不写入用户资料正文以外的内容。

### 3.5 知识库跟随解包更新

目标：用户能知道“有没有新数据、新了什么”，更新可靠、可恢复、尽量省流量；只读不变量成立。

1. **更新检查**：对比已装库的 `source_arknights_commit` 与上游最新 commit（App 内构建通道已有 compare API 逻辑），
   在知识库页显示“上游有 N 个文件变化”；release 通道对比 `.asset_sha256`（已做）。
2. **App 内增量更新**（已有）：整理成稳定通道——后台服务保活（v0.10.6 已有）、可取消、失败保留旧库、产物经
   `validateGameDataDatabase` 后原子替换；补上 `library_index` 与 `story_catalog` 的增量维护；输出**差异报告**
   （新增/改动的故事和档案数量，文档里早已列为要求）。向量表仍只来自 release 资产。
3. **整包**：保持；M5 前先测“整包 185 MB vs 增量”的真实代价再决定要不要做增量包（文档原先的待决事项）。
4. **“实时”**：是否由 CI 定时检测上游并滚动发布新资产（`gamedata-latest`），需要开发者决定——它要仓库 secrets、
   向量构建需要 embedding key（花钱）。默认建议：**先不做**，只做 1–2；有需要再单独立项。

## 4. 里程碑（每个一个 PR，开发者合并；发版另需开发者同意）

| 里程碑 | 内容 | 验收 |
| --- | --- | --- |
| **M0 启动**（本次） | 角色扮演结论；本计划；文档与状态更新 | 文档合并 |
| **M1 用户库与历史** | `userdata` 库 + 迁移框架；阅读历史/书签；把 `_ensureStoryLinesIndex` 收口；资料页壳（tab：阅读/历史/我的资料）；证据链打开原文时记入历史 | 单元测试（迁移、读写、官方库更新后引用降级）；真机能“继续阅读” |
| **M2 剧情目录** | `library_index`（剧情部分）+ 构建器；剧情浏览树（主线/活动/密录/肉鸽…）；阅读器：上一章/下一章、章内搜索、进度；离线可用 | 目录与 `story_catalog` 一致；任意章节可打开；排序/分组不含特判 |
| **M3 档案阅读** | 档案/语音/敌人/道具等文档目录与文档阅读器；全局搜索（官方内容） | 各 `content_type` 至少一类可读；搜索中文可用（视 FTS 测量） |
| **M4 用户资料** | 导入/编辑/删除/标签/搜索；问答页“附上资料”；低可信标记 | CRUD 测试；附上资料后回答的官方出处仍通过 `SeenLines` 校验 |
| **M5 更新通道** | 更新检查、增量更新稳定化、差异报告；整包 vs 增量测量；决定是否做滚动资产 | 在真机上从旧库更新成功，用户库不受影响 |

0.11 的发布方式沿用 0.10：先以预发布验证，**正式版和删旧版本由开发者决定**。版本号：0.11.0 起，Android build 号继续递增（当前 22）。

## 5. 不变的约束

- 官方库只读；用户数据只进用户库；引用用稳定标识。
- 阅读目录、搜索、历史都是导航，**不是证据**；证据只来自 Agent 读到并通过 `SeenLines` 核对的原文。
- 不为具体剧情/人物写分支；不在数据层预置场景词表；目录规则对任意活动、任意故事集成立（见 `CLAUDE.md`）。
- 长时操作（导入大文件、更新知识库）包在 `BackgroundWork.instance.run(...)`。
- 真实 API 测试仍遵守成本约束；本阶段（资料页）基本不需要。

## 6. 开放问题（有默认值，开发者可改）

1. 是否做 CI 滚动资产（默认：不做，先做 App 内更新检查）。
2. 用户资料导入格式（默认：txt / md，先不做 PDF）。
3. 角色扮演页是否在 0.11 内从界面移除（默认：保留冻结，资料页稳定后再定）。
4. 阅读器的“字号/行距/主题”设置是否随 M2 一起做（默认：做字号，其余沿用主题）。
