# 知识库建库、更新与修改：0.11 的经验、注意点与错误

> 写给下一次建库的人（0.12 起：终末地）。0.11 把明日方舟知识库从“按字段拍平的行”重做成“按条目建模”（schema 5），
> 并做了增量更新、补算工具与向量迁移。这里记录**做对了什么、踩了什么坑、哪些规则必须保留**。
> 具体表结构与命令见 `GAMEDATA_BUILD_PIPELINE.md`；本文只讲经验。每条错误都写了“怎么发现的”，因为发现手段本身就是经验。

## 0. 一页结论

1. **先普查，再建模。** 把上游整棵树下载到本地（`notes/upstream/`），逐表逐目录量“有多少字、库里有多少”，按“叙事 / 设定 / 玩法 / 关联”分层，
   让开发者定档。0.11 第一步的普查直接决定了 schema 5 的形状，后面没有返工结构。
2. **条目是单位，id 是唯一可信的关系。** 每个官方条目一行（`entries`），归属（`collections`）与绑定（`entry_links`）只能由表里的 id 算出，
   不能用名字猜，不能写活动名/人物名表。
3. **全量构建、增量更新、补算（rederive）必须是同一套代码，并且结果逐行一致。** 这一条要靠实验证明（§4），不能靠“看起来一样”。
4. **任何重导入都要先清掉上次写的东西**（`_purgeSource`），否则规则一变旧行就留下来。
5. **不收玩法文字。** 先量化“这类文字对剧情有没有用、会不会淹没检索”，再决定（敌人技能描述就是被数据否决的）。
6. **向量是派生物，跟着行号走。** 改了文字或解析规则，就要让向量按行对齐迁移，而不是重嵌入（§5）。
7. **名字以游戏表或 wiki 为准，查不到就不起名。** 无标题好过臆造。
8. **每一次规则修改都要回答“已有的库怎么补算”**，并且补算后的库要和全量新建库一致。

## 1. 普查（建库前）

- 上游（`Kengxxiao/ArknightsGameData`）约 1 GB，有用的文字只在 `story/`（63 MB）与 `excel/`（144 MB）；`levels/`（约 500 MB）只提供
  “关卡里有哪些敌人/装置/召唤物、播放哪篇剧情”的关联；`bakemuzzledata/`、`building/` 等不进库。**先量目录再决定下载什么**，不要 clone。
- 普查的方法：每个 excel 表随机抽 ≤120 个文字片段，看库里能否找到（“抽样命中率”）；剧情脚本按命令标记统计丢了多少行/字。
  这样量出了旧库的真实缺口：剧情脚本丢 4%（23,577 行、52 万字，主线丢最多）和 885 个整文件；活动档案、新闻、来信、事件文本几乎为 0。
- 上游更新节奏：约每周一次，普通一次 2–4 个剧情文件、10–24 个表；客户端大版本时一个提交改几千个文件（见 §3 compare 截断）。
- 普查脚本放 `notes/*.dart.txt`（改后缀运行，不被 analyze 扫描），结果放 `notes/`，**不提交**。

**终末地要先做同样的普查**：数据从哪来（解包仓库 / 本机解包）、目录结构、文字在哪些表、有没有剧情脚本、id 体系、更新频率。

## 2. 建模规则（schema 5 的设计原则）

### 2.1 什么进库

- 进：名字、设定/背景描述、剧情脚本全部带文字的行、新闻、来信、事件叙述、档案、物品/皮肤/奖章/藏品描述、世界观、干员档案与语音。
- 不进（开发者决定，`CLAUDE.md` Do Not）：技能、天赋、基建、商店、规则/任务说明、效果与数值、获得方式、**敌人技能描述**。
- 敌人技能描述是用数据否决的：3720 条中 75% 是机制用语；“召唤/复活/重生/隐匿”这类词，技能描述的命中数是剧情台词的 3–7 倍，
  会淹没检索且没有设定内容。**新数据源先做同样的“命中淹没”测量。**
- 教程/引导文字进 `story_lines`（`kind=system`），但不进检索块和向量。
- 留待决定：干员“特性”文字（`description`）属于玩法，但召唤物/装置条目只有它，去掉会让条目消失（0.11 保留并清理标记）。

### 2.2 条目、集合、绑定

- `entries.id = <type>:<原始 id>`；`collections.kind` 决定书架（主线、SideStory、故事集、插曲、其他活动、干员密录、集成战略、生息演算、系统）。
- 归属：关卡 → `zoneId` → `zoneToActivity` / 主线章；其余条目按“id 前缀等于某个已知集合 id”；物品看 `stageDropList` 所在集合（唯一时）、
  再看唯一一个在活动表里点名它的活动；奖章看 `medal_activity_<活动>`，否则看通关条件里点名的东西。
- 绑定只来自表或关卡文件：`appears_in`（敌人/装置/召唤物 → 关卡，来自 `enemyDbRefs`、`SPAWN`、`predefines`）、`plays_in`（剧情 → 关卡，来自关卡的 `STORY` 动作）、
  `belongs_to`、`part_of`（结局书页面、月度小队故事）、`summoned_by`、`same_person`（`char_meta_table.spCharGroups`）、`features`、`reads_story`。
- **复刻不是独立内容**：复刻活动的文本、奖章、掉落并入原活动（`ctx.alias` / `ctx.home`），复刻的关卡不单独出条目。
- **派生关系在最后一步统一算**（`rebuildDerived`）：故事命名、关卡内对话挂到宿主剧情（`attached_to`）、同名去重（`item_twin`）、分组名替换。
  把它们放在导入过程中算，会依赖表的导入顺序。

### 2.3 名字

- 名字优先级：表里给这个文件/条目本身的名字 → 所属关卡/结局/任务 → 只能判断类型时按类型编号（`训练 3`，自然序）。实测把非中文名的故事从 1676 降到 39。
- 界面里所有由代码推出来的名词都去 prts.wiki 核对（“勋章”→“奖章”、“护符”→“标志物”、“背景”→“首页场景”…）；查不到的不显示标题。
  构建工具 `rederive_gamedata.dart` 末尾打印 `unnamed kind: …`，新主题出现时逐个去查。
- 未知的东西要有兜底：未知书架显示“其他”、未知类型按家族显示、未知绑定显示“相关”，**绝不显示原始 id**。
- 不建别名/身份表（代号、真名、冒名、夺舍都是剧情解读）；数据层只保证检索能走通（近似名）。

### 2.4 剧情脚本解析

- 不能用白名单正则（旧解析器只认 `[name="X"]文本`，新写法一律丢）。现在 `story_script.dart` 读所有带文字的命令，每行带 `kind`
  （dialogue / narration / subtitle / document / choice / title / system）。
- 命令可以跨行（行尾 `\` 续行），要先合并逻辑行（`storyLogicalLines`），否则属性行会被当成旁白（全库 1471 行、319 个故事中招）。
- 引号里的换行写成字面 `\n`（书信、诗、笔记），必须转成真换行（1853 行中招，见 §6）。
- `<名字>` 不是标签：`stripMarkup` 只删真正的标签（`<@x>`、`<$x>`、`</…>`、`<color=…>`、纯 ASCII 标签），否则“<热泵通道>”整段消失。
- 输出给 Agent 的工具格式是“一行一个 `L<n>`”，行内换行印成 ` / `（`oneLine`），否则模型会把内部换行当成新的一行。

### 2.5 表格文字

- `text_harvest.dart`：活动表等长尾结构按“路径关键词（news、letter、dialog…）或成段句子”收集，路径里有玩法词或文字含数字/百分号/效果用语的丢弃。
  这是通用规则，不为某个活动写特例。
- 重复：皮肤文本的几个字段互相重复段落（按行去重）；肉鸽收藏品新旧两表、按朝向/槽位重复（一个主题 3502 → 539）；物品同名同文字同集合只留一条。
  **去重条件要包含“文字完全相同”**，否则会把同名不同物合并。
- 肉鸽事件的选项层级表里没有直接给出，是按选项在表里的排列推出来的（`event_outline.dart`）；这种“推断结构”要在文档里写明依据。

## 3. 增量更新（App 与命令行同一套：`SourceSync` → `GameDataBuildService`）

1. 读已装库 manifest 的上游提交 → 取最新提交 → 比较两棵文件树（excel/story/levels 三个文件夹按 blob 哈希比，约十个请求）。
2. 只下载变化的文件 + 缺的“上下文表”（归属、名字要读的表），6 个并发。
3. 复制旧库，按“数据表 → 关卡文件 → 剧情文件”逐个应用：删除该文件产生的行再重导；上下文表变化时**按完整构建的顺序重读全部条目表**。
4. 整体重算派生层、目录、FTS；校验后原子替换；写更新报告；向量单独补（只补缺的故事）。

**这一节里的每一条都是踩出来的：**

| 错误 | 怎么发现的 | 修复 |
| --- | --- | --- |
| GitHub compare API 一次最多返回 300 个文件；一个提交里有几百个 `bakemuzzledata` 文件，就把所有表和剧情挤掉，App 说“没有相关变化” | 一致性实验（§4） | 改为读两个提交的文件树按哈希比，与提交大小无关；旧提交消失 → 完整重建 |
| `[uc]info` 目录下的文件下载 404（路径被二次编码） | 一致性实验 | 路径只编码一次 |
| 活动表/关卡表/分区表变了而物品表、奖章表没变时，后者的归属不重算 | 一致性实验 | `EntryTables.contextTables` / `ownerDependents`：上下文表变化时重读依赖它的表 |
| App 内完整重建的 zip 提取不含 `levels/`，建出的库没有敌人/装置/召唤物绑定 | 一致性实验 | 提取 `levels/`，建完删除 |
| 导入一张表时没有先清掉它上次写的行（只有肉鸽表清），规则变过之后旧行留着：更新库和补算库都比新建库多 1340 条复刻关卡、213 个故事名不同 | 第二轮一致性实验 | `_importTableWith` 先 `_purgeSource`（条目、记录、本表写的绑定、实体与别名） |
| `_purgeSource` 曾按 `src/dst IN (被清的条目)` 删链接，把关卡文件写的 `appears_in` 一起删了，肉鸽关卡丢了敌人 | 真机发现肉鸽关卡没有敌人 | 只删 `source_path = 本表` 的链接，其余按 id 重新对上 |
| 先到先得的重复 id，结果取决于导入顺序 | 一致性实验 | 增量时也按完整构建的顺序重读（`importAllTables`） |
| `system` 集合的排序号取决于行的物理顺序 | 一致性实验 | 按 story_id 排序 |
| 库里的 `source_path` 在 Windows 上是反斜杠写法，删除旧行时只认正斜杠 | 补算后旧行残留 | 两种写法都认（`deleteStoryRows`） |

- GitHub 匿名额度每小时 60 次；一次检查/更新只用十几次。token 只在单条命令或请求头里使用，不打印。
- 下载要能看到阶段、能取消、能续传（手机到 `release-assets.githubusercontent.com` 的连接会卡住不应答；每次重连用新连接，连接超时 45 s，最多 6 次），
  并且给出“手动下载放进应用目录”的退路。

## 4. 一致性实验（最重要的验证手段）

**做法**（`build/consist/`，不用向量，约一小时）：

1. 从上游较早的提交建“早库”（0.11 用的是 11 周前的 `fa63359`）。
2. 用 App 同一套增量代码（`tools/update_gamedata.dart`）把早库更新到最新提交。
3. 从最新提交全量新建一个库。
4. 用补算工具（`rederive_gamedata.dart`）把一个旧规则建的库补算到新规则。
5. 逐项对比（`cmp.dart`）：条目、故事行、记录、绑定、集合——**全部一致才算通过**。

它在 0.11 里抓到了 §3 表里几乎所有问题，单元测试一个都没抓到（单元测试的夹具太小，没有“一个提交几百个无关文件”“规则变了旧行还在”这种情况）。
**每次改建库代码的结构（不是只改某条名字规则）都要重跑一次。** 终末地的构建器也必须从第一天起就能做这个实验。

## 5. 向量

- 向量表 `story_chunk_vectors` 按 `(story_id, 起止行号)` 存，12 行一块、步长 8；模型/维度/切块写进 manifest，App 只在配置一致时启用。
- **按内容哈希缓存会全部失效**：两次构建之间上游把全文“......”统一成“……”，缓存命中只剩 6.8%。所以改为**按行对齐迁移**
  （`build_story_embeddings.dart --migrate-from=<旧库>`）：同一故事的新旧行按顺序对齐（忽略省略号点数、空白、字面 `\n`），
  首尾两行都对得上的旧向量原样搬到新行号上，对不上的才调 API。0.11 两次迁移：51,264 条全迁 + 4,309 块新嵌入；54,846 条全迁、0 块新嵌入。
- 剧情文件重解析会删掉该故事的向量（行号变了）——**每次改解析规则都要接一次迁移**，否则知识库发出去少了一块向量。
- 迁移的对齐规则要跟着解析规则一起改：字面 `\n` 改成真换行后，对齐函数 `_norm` 也要把字面 `\n` 视为换行，否则 162 个故事对不上。
- 费用：0.706 token/字；百炼 ¥0.0005/千 token（估算，以账单为准）；全量约 5.5 万块、约 ¥5。真实 API 调用要开发者同意。

## 6. 修改已有的库（补算）与发布

- 规则修改后，已有库用 `rederive_gamedata.dart --db=<库> --source=<源> --output=<新库>` 补算：重导全部条目表（`importAllTables`）、
  重解析与库里行不同的故事（`reimportChangedStories`）、重建派生层与 FTS，不动向量（被重解析的故事的向量会被删，要接迁移）。
- 补算后检查（以字面 `\n` 修复为例）：三张表里字面 `\n` 的计数为 0；迁移后向量条数与旧库一致；`flutter test` 与验收测试通过。
- 发布知识库：gz（.NET `GZipStream`，Windows 没有 gzip）→ `finalize_gamedata_assets.dart` 写 manifest → 上传到 Release → `tools/release_gamedata.env`
  改 URL 与 SHA → 再构建 APK（APK 只认这个 SHA）。**URL 必须先指向将要创建的 Release**，CI 把它烘进 APK。
- 本机试装：`tools/install_local.ps1 -Build -Kb`（要连手机）。旧库留作 `.preN` 备份，便于对比与回退。
- 每次发知识库前确认：schema 版本、必需表、向量条数、目录条数、manifest 的上游提交。

## 7. 其他教训

- **测试夹具一律用生产 schema**（`test/support/gamedata_fixture.dart`）。手写建表的测试曾和真实表分叉（列不同、FTS 分词器不同），测试过了而 App 是另一回事。
- `story_lines(story_id, line_index)` 曾没有索引，每次读章全表扫描（0.45 s 一次，一次回答几十次）。新表一律检查查询路径上的索引。
- 中文 FTS（unicode61）基本无效；靠 LIKE + 可选向量。
- 大文件（剧情向量索引约 28 MB）不要经 sqflite 平台通道传进 UI isolate，用 FFI 在后台 isolate 读。
- 用户数据（阅读历史、我的资料）放独立的库（`userdata/arklores_user.db`），只存引用字符串（`story:<id>` 等）+ 原文片段，
  知识库变动后按片段重新定位。**知识库的 id 必须稳定**，否则用户的历史全部失效。
- 构建在 Windows 上约 7 分钟（全量）；`--story-limit=30` 约 30 秒，适合调规则（不能用于验收）。
- 修改规则时先在 `notes/` 写个探测脚本对全库计数（“这条规则影响多少行”），再改代码；改完再计数确认。

## 8. 给终末地（0.12）的检查清单

- [ ] 普查：数据源、目录、文字分布、id 体系、更新频率；写进 `notes/`，结论进本仓库文档。
- [ ] 分层定档：叙事 / 设定 / 玩法 / 关联，开发者确认玩法不进。
- [ ] 与明日方舟库的关系：**独立的库文件**还是同库不同 `game`？（证据来源必须能区分，跨游戏不能混搜出错证据）
- [ ] 条目、集合、绑定只来自 id；名字以官方/wiki 为准；未知有兜底。
- [ ] 剧情脚本格式：命令语法、续行、转义、标签与名字的区别、行类型。
- [ ] 全量构建、增量（如果有可增量的上游）、补算同一套代码；一致性实验通过。
- [ ] 向量：同样的切块与迁移；manifest 记模型。
- [ ] Agent：提示词里讲清两个游戏的库结构，工具能指定查哪个库；出处带游戏。
- [ ] 资料页：书架按游戏分开；用户数据引用带游戏前缀。

## 9. 两个游戏（0.12 的设计决定）

- **每个游戏一个库文件**（`arklores_gamedata_zh.db`、`arklores_endfield_zh.db`），表结构相同（schema 5）。分开是因为更新节奏、数据来源、体积都不同：
  明日方舟可以从社区仓库增量更新，终末地只能在电脑上从游戏客户端解包重建；合在一个库里，任何一边更新都要重下整包，增量更新的“先清后导”也会误删另一个游戏的行。
- **终末地的每个 id 都以 `ef/` 开头**（story_id、collection_id、collections.kind、条目原始 id、记录 id）。于是任何地方拿到一个 id（出处、阅读历史、
  资料页路由、搜索结果）就知道该去哪个库，不需要额外的字段或查表（`game.dart` 的 `gameOfId`）。story_id 仍以 `.txt` 结尾，沿用所有按 `.txt` 识别故事的代码。
- **Agent 看到的是一个合并的检索面**（`MultiGameRetrieval`）：按 id 的调用去对应的库，全库统计与检索两个库都问并合并；`sql` 一次只查一个库（`game` 参数），
  `grep`/`find` 可选 `game`。提示词里的“两个游戏”一节只在装了终末地时出现，讲清 `ef/` 与“判断问题属于哪个游戏，看不出来就两个都查”。这是数据来源的说明，
  不是问题类型的特判。
- **资料页按游戏分组**：阅读页每个已安装的游戏一组书架；终末地的书架 kind 也带 `ef/`，所以书架页、集合页、条目页、搜索范围都按 id 自动走到对应的库；
  图鉴书架是 `ef/codex`；搜索“全部”时两个库都搜并合并。
- **出处标签带游戏名**：终末地目录的 collection_type 以 `EF_` 开头，标签前缀“终末地·”。
- 知识库页每个游戏一张下载卡（`GameAssetCard`），终末地资产的 URL/SHA 在 `release_gamedata.env` 的 `ENDFIELD_DB_URL/SHA256`。
