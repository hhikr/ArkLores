## 1. 知识库与检索

| 问题 | 根因 / 现状 | 缓解与方向 |
| --- | --- | --- |
| 没有中文全文索引 | FTS5 `unicode61` 不分中文词，原来的三张索引表没有用，0.14 已删 | 原文检索用 LIKE（按命中行数排序）+ 可选向量；中文分词 FTS（trigram）未做，LIKE 在 44 万行上全表扫描（桌面 <1 s，真机单次约 2.3 秒，是检索耗时的大头） |
| 没有组织/概念级汇总实体 | 组织、地点、概念没有可枚举的表，只能从文本涌现 | Agent 用 `grep` 全库统计 + 读原文；不建人工词典（会把方向写死） |
| 人物身份只能在问答时确认（设计如此） | 代号/真名/“？？？”/冒名/夺舍都是剧情解读 | 只保证检索可达（读音近似名）；揭示身份的那一行没读到时，答案停在“资料未覆盖” |
| 干员“特性”文字（玩法）仍在库里 | 召唤物/装置条目只有这一段，去掉条目会消失 | 待开发者决定；可改为只给 token/trap 保留 |
| 推断出的结构 | 肉鸽事件的选项层级、生息演算事件的场景顺序，表里没有直接给出，按排列推断 | 规则写在 `event_outline.dart` 与文档；出现明显错层时再按新表结构修 |
| 没有向量 key 时只有字面检索 | 向量需要用户配置服务 | `search` 写明退回原因；写错的名字靠近似名 |
| 知识库下载在部分网络上卡住 | 手机到 GitHub 资产域名的连接不应答（未能复现根因） | 阶段显示、45 s 超时、6 次新连接、取消、手动放置 `.download.gz` 的退路 |

## 2. 问答 Agent

| 问题 | 现状 | 方向 |
| --- | --- | --- |
| 耗时 | GLM 一题 4–6 分钟（带工具的调用有 4.5–6 s 底噪；答案文本写 3 遍） | 0.14 起复核/提要不在提问里运行，是答案下方的按钮；降本改动需单独立项 |
| 审稿依赖模型对作品的记忆，提什么有波动 | R18 审稿子 agent 只提故事层面的问题，结论仍由主 agent 读原文决定 | 不加针对某类剧情的检查项（CLAUDE.md） |
| 回答语言跟随提问语言 | 2026-10-10 答案格式加了“用用户提问的语言写”（较弱的模型用英文思考时曾把答案写成英文；加上后同一模型答案是中文，思考仍是英文）；未按界面语言 | 需要时改为按界面语言 |
| 较弱的模型一次回复里写多份答案 | 先写说明（会照抄格式骨架）、再写几份不完整的 JSON、最后才是完整答案；解析取最后一个完整且有条目的版本（2026-10-10），流式显示时用户先看到的仍是第一份，答完后才被替换 | 需要时在流式阶段也只显示最后一份 |
| 在问答进行中保存设置可能中断当前问答 | 设置变化会重建 client provider | 保存时若有进行中的问答，延后生效 |
| 评测集标准答案未人工审核 | `test/fixtures/investigation_eval.json` 是草稿 | 只作参考，不作通过门槛 |

### 已知的问题

| 问题 | 现状 |
| --- | --- |
| 渠道文件还没有上线 | 2026-10-17 起 App 读 `gamedata-channel` Release 上的 `gamedata_channel.json`，只上传新库也能被发现（`GAMEDATA_BUILD_PIPELINE.md` §4.4）。云端建不了 Release，这个 Release 和第一份文件要开发者建；从第一个带它的版本起才生效，v0.14.0 及更早的 App 仍只认包里的资产。真机没试过 |
| 官方资产与本机更新的先后 | 2026-10-17 起本机更新把所拉提交的日期写进清单，比较两边提交的日期，不再看手机时钟。这之前更新过的库清单里没有日期，仍按“更新是在什么时候做的”比，下一次本机更新后就有了 |
| 关键词扫描是检索里最慢的一段 | 手机上每个库 1.3–6.3 秒（并行的检索更慢），Wiki 0.5–8 秒，剧情向量 0.08–0.2 秒（瘦身前量的）。终末地库小得多耗时却接近，像是在同一个连接上排队，没有查代码确认。入口 `SearchTool._rank` → `searchStoryLinesLike`。能切中文的全文索引（trigram）在手机的 SQLite 上是否可用没有验证 |
| 出处只核对“看没看过” | 代码查的是所引的行是否展示过，不查这些行是否支持那句话。真机上有：所引的故事里没有被解释的那个词、把一个人的话引到另一个人的台词上、直接接受提问里的前提。靠“复核”按钮或读者自己点开出处 |
| 英文提问用中文作答 | 历史问题集里唯一的英文题两次都是；提示词里已有“用提问的语言写” |
| 集成战略的结局文本有时和主线混着讲 | 有的答案写明“一条结局线”，有的当成已经发生的事。阅读原则里没有这一条 |
| 拟定的第一批查找带进无关的词 | 约三分之一的题：很泛的名字（阵营、种族、主角名）、资料种类的词、不相干的人物；按章节问时目录名是编的；玩家没提 Wiki 时也会写一条 `wiki_search`。评测集上至少列出一篇金标的是 25/29（带向量）。每问多一次小调用（超过 25 秒或写不出来就退回原文检索） |
| 模型照不照线索去找不稳定 | “各给一段”之后按人物问的那题 4/4 讲全，代价是输入约 2–3 倍；只有这一道题、一个模型验证过。段数和每段行数要不要收没有定 |
| 库里没有的内容要找很久才放弃 | 一道问库里还没有的故事的题用了 41 步、98.8 万输入；没说查什么的“请查 Wiki”追问 282 秒。没有结果的查找的上限只管同一个工具连续落空 |
| 长整理题很贵 | “整理某人在主线若干章里的行动”二十多次 `grep`、27–55 万输入 |
| 路径写短的出处被删 | 模型把故事路径少写一段目录时，那条出处直接删掉（17 题里 3 题各丢 1 处）；没有按“读过的故事里唯一的文件名”补回 |
| 向量服务偶尔出错 | 那一题退回关键词检索并提示，不重试（40 次运行里 2 次） |
| “提要”“复核”只对本次运行期间的答案有 | 两者要用写出答案的那段对话和条目，这些只在内存里；从历史恢复的会话、重启之后的旧答案下面没有按钮 |
| 核查结论要模型自己写 | 提示词约定核查说法时 JSON 以 `verdict` 开头；模型把“有人说……对吗？”当普通问答时界面没有核查标记。按 R13 不由代码判断“这是不是核查题” |
| 略去较远的游戏用的是固定差值 | 0.08 是对当前嵌入模型的经验值；问题的词两边都常见、答案其实在较远的那个游戏里时会被略去，靠那一行提示再查 |
| 终末地库的档案合集 id 没有 `ef/` | `entity_documents` 的 `id`（33 条，哈希）不带前缀，`entity_id` 带 `ef/`（2026-10-17 复核）；引用写成 `record:ef/<哈希>`。`search` 列出时补上、引用弹窗两种都查；`sql` 直接查出的这种 id 引用后会落到明日方舟库。建库代码已改（2026-10-17，`endfield_writer.dart` 的档案 id 包上 `endfieldId`，构建测试检查）；v0.14.0 的资产仍是旧的，重建终末地库并发版后生效 |
| 一个活动仍没有关卡 | 复刻活动的关卡修正后 52 个 SideStory 里 51 个有关卡；剩下的一个没有查原因 |
| 没有向量服务时检索偏弱 | 只有字面匹配，检索词由模型写；界面提示“问答质量可能下降”。较弱的模型检索词也对，但答案质量差 |
| 总是返回空回复的服务商每轮多花两次请求 | 空回复先原样重试、再降级，只对这一轮 |
| 取消后在途的请求不会被中断 | 事件流立即断开、用量当场记下，但已发出的 HTTP 请求会在后台跑完（结果丢弃），其用量可能记到下一个问题上 |
| 真机问答只能经桥测试 | `tools/phone_ask.dart` 驱动的是带桥构建的 App，与发布的包只差这一层；发布的包在真机上仍要手动看一遍 |
| 全量测试在高负载时有偶发超时 | 机器很忙时全量测试从约 1 分钟拖到 3 分钟，写入多的用例可能超过 30 秒超时（单独跑通过） |
