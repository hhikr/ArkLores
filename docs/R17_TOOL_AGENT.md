# R17：工具型剧情 Agent（一个模型 + 通用工具 + 只追加的对话）

> 状态：v0.10.1 起是剧情问答**唯一**的流程。R13–R16 的分步流程（`PlannerLoop`、状态、提取器、writer）已删除，
> 原文和逐步说明（`ASK_PIPELINE_FLOW.md`）都在 git 历史中。

## 1. 为什么改

用户让几个通用 agent 直接读 GameData 库回答剧情问题，它们都只拿到一句很简单的提示词：

- deepseek-harness：不思考、不思考加子 agent、低档思考三档；
- 两个匿名 agent。

问题是“塔露拉在切尔诺伯格事件之后做了哪些事情？”，日志在 `logs/成熟的agent如何处理/`。

结果它们全都比 R13–R16 的分步流程好。R13–R16 补丁越打越多，样例问题变好了，别的问题和追问反而变差。

读日志后发现，这些 agent 的做法几乎一样：

1. **先看全局。** 用一条聚合 SQL 拿到全语料的地图：含某个名字的行按 `story_id` 分组计数，关联 `story_catalog` 按顺序排。不需要猜 story_id。
2. **整章读，章内搜。** 把整章导出，再在章内 grep 或按偏移读，一次 8–16k 字。
3. **读原文的模型就是写答案的模型。** 没有摘要器，也没有 writer 从材料里选段落。
4. **对话只追加、不重排。** 所以 97% 的输入命中前缀缓存：DSH 不思考档新增 7.5 万 token，缓存命中 214 万。
5. **没有手写的进度规则。** 不设预算，没有重读阶梯，不做复核。由模型自己判断还缺什么。

R16 正好相反：

- 决策器只看压缩后的状态；
- 原文先变成摘要，再由 writer 从 6 万字里选材；
- 每步重建提示词，缓存失效。

结果是贵，信息还在一道道交接中丢失。补丁之所以只对样例有效，原因就在这个结构上。

## 2. 结构

```
用户问题 ─► AskChatNotifier
            ─► StoryQaAgent.run ─► LoreAgentLoop
                 第一批检索（0.14）：一次独立的小调用按问题拟定检索词，代码执行，作为 search 调用和结果进入对话
                 system: loreSystemPrompt()（库结构说明 + 工作方式 + 引用格式 + 输出格式）
                 messages: [上一问的对话，工具结果已折叠（追问时）] + 用户问题 + 每轮 assistant/tool 消息（只追加）
                 每轮：client.streamTurn(messages, tools) ─► 文本增量 / tool_calls
                       有 tool_calls → 守门（拆分粘连、按 schema 校验）→ 同一轮的调用并发执行，结果按顺序追加
                       没有 → 最终答案 → 出处核对（少量未核实的出处由代码删去；多了才退回一次）→ 状态信封
```

0.14 的改动与原因见文末“## 5. 0.14 重构”。下面各节的表格与数字是写成时的状态，已被 §5 修改的地方以 §5 为准。

| 文件 | 作用 |
|---|---|
| `lib/core/agent/lore_agent_loop.dart` | 循环、文本协议回退、上下文折叠、出处核对、状态 |
| `lib/core/agent/lore_tools.dart` | 工具；`SeenLines` 记录本次给模型看过的行和记录 |
| `lib/core/agent/lore_agent_prompts.dart` | 系统提示（所有问题同一份，R13） |
| `lib/core/gamedata/readonly_sql.dart` | 只读 SQL：语句检查，每次查询一个后台 isolate，超时用 `sqlite3_interrupt` 中止 |
| `lib/core/llm/openai_client.dart` | `streamTurn`：SSE 中按 index 拼接 `tool_calls` |

### 工具

| 工具 | 作用 | 上限 |
|---|---|---|
| `sql(query)` | 一条只读 `SELECT`/`WITH` | 200 行 / 16k 字，8 s 超时 |
| `grep(pattern, story_ids?/collection?, context, max_hits)` | 子串匹配，`\|` 表示任一。不给范围：全库按故事统计行数（主线在前，其余按上线时间）；给范围：命中行加上下文，命中行标 `*` | 150 行，列出 160 个故事 |
| `read_story(story_id, start, count)` | 连续读原文，`L行号 [说话人] 内容` | 500 行 / 16k 字 |
| `find(query, collection?)` | 按意思找：FTS 关键词，配置了向量 API 时再融合语义召回（复用 R12 `SearchStoryLinesTool`）；只是定位线索 | 6 个故事 |
| `outline(collection)` | 故事集章节、关卡号、官方梗概（只用于定位） | 16k 字 |
| `similar_names(name)` | 读音或字形相近的名字（R15 `name_similarity`） | 8 个 |
| `delegate(task, story_ids?, collection?)` | 把一部分阅读交给子 agent（只主 agent 有） | 子 agent 20 轮 |

两个游戏（0.12）：`sql` 有 `game` 参数（`arknights` / `endfield`，默认 arknights），一条 SQL 只查一个库；`grep`、`find` 的 `game` 可选，不给时查所有已安装的库并合并；
`read_story`、`outline` 按 id 自己找库（终末地的 id 以 `ef/` 开头）。检索面是 `MultiGameRetrieval`；装了终末地时系统提示多一节“两个游戏”
（`loreGamesGuide` + `lore_endfield_prompts.dart`：终末地库的结构，判断问题属于哪个游戏，看不出来就两个都查）。

Wiki（0.13，输入框“回答选项”的“Wiki 资料”开着时；设计见 `WIKI_EVIDENCE.md`）：

| 工具 | 作用 | 上限 |
|---|---|---|
| `wiki_search(query, game?, limit?)` | 在 PRTS（明日方舟）或 Warfarin Wiki（终末地）上搜索，返回页面引用 `wiki:<站点>:<页面>`、标题、摘要（摘要不能当出处） | 15 个页面 |
| `wiki_read(page, game?, start, count, section?)` | 读一个页面：开头给页面 id（含版本）、网址、小节目录，正文 `P段号 内容`，`## 标题` 行是小节；`section` 只读某些小节 | 250 段 / 16k 字 |

系统提示多一节 `loreWikiGuide`：Wiki 是二手资料，库里能读到原文的引用原文；不一致时以原文为准；只有 Wiki 支持的说法写明“据 Wiki 整理”；
联网失败时不重试、只用库作答。关掉开关时这两个工具和这一节都不出现。

### 子 agent

`delegate` 启动一个新的 `LoreAgentLoop`（`subtask: true`）：

- 有自己的对话，工具与主 agent 相同，但没有 `delegate`（只有一层）；
- 系统提示要求只完成交给它的查找，最后交回带出处的要点；它也走自己的出处核对；
- 结束后它看过的行和记录并入主 agent 的 `SeenLines`，所以主 agent 可以直接引用它交回的出处；
- 同一轮的多个调用并发执行，事件和 tool 消息仍按调用顺序给出。

是否拆分由模型决定。实测：读二十章左右的问题它自己读完；“凯尔希在第 9–15 章的主要行动”派出了 5 个子 agent。

### 写错的名字

缪因、切尔诺贝利这类写错的名字，没有专门的匹配代码，靠三件事解决：

1. 提示词允许模型用自己对作品的了解**构造查询**，但这些了解不能当证据。
2. 0 命中会如实写“0 行”，并要求先换写法再下结论。
3. `sql`、`grep` 零命中时自动附上 `similar_names` 的提示。

实测效果：

- 切尔诺贝利 → 切尔诺伯格（剧情提及 374 次）；
- 缪因 → 谬因（干员）。

答案用原文写法，第一次提到时括号注明用户的写法：“X（你写的是 Y）”（R17b 起；之前是开头写“库中写作 X”）。

### 出处

- 剧情台词：`story_id:起始行-结束行`。行号是 `line_index`，从 0 开始。
- 其他资料（`normalized_records`）：`record:<id>`。
- Wiki 段落（0.13）：`wiki:<站点>:<页面>@<版本>:起始段-结束段`，JSON 里写 `["<页面 id>", 起始段, 结束段]`，段号从 0 开始（界面上从 1 显示）。

核对规则：

- 行必须由工具连同正文给模型看过：`read_story` 的页面、`grep` 的命中和上下文、`search` 列出的行、`sql` 结果中同时带 `story_id + line_index + content` 的行。
  范围里只有一部分行看过时，代码把出处裁成看过的那几段（0.14；以前整条作废）。
- 记录 id 必须由 `search` 列出（记为片段）或出现在查 `normalized_records` / `entity_documents` 且带 `content` 的 `sql` 结果里。
- Wiki 段落必须由 `wiki_read` 展示过（按页面 id 含版本记录）。
- 只写文件名、没有行号的出处、读过资料却一条出处都没有的答案会被退回。
- 每个问题最多退回一次（整轮回档，见 §5 末）；仍无法核实的出处会附注在答案末尾。

### 状态信封

- **not_covered**：没有任何核实过的出处。
- **partial**：模型自己写了 `[COVERAGE: gaps]`，或者到了轮数上限。
- **answered**：其余情况。

### 安全阀

只有下面几个，不设预算提示，不拒绝重读，也不做复核：

- 每问最多 60 轮，最后一轮 `tool_choice: none`，要求直接作答；
- 只读 SQL 超过 8 秒，用 `sqlite3_interrupt` 在 SQLite 内部中止语句（工作 isolate 在主 isolate 允许前不关闭连接，所以中止不会碰到已释放的连接），并告诉模型缩小范围；
- 上下文超过 36 万字时，把最早的工具结果折叠成一行指引，最近 8 条消息不动；
- 用户可以随时停止。

### 追问

`AskChatNotifier` 按回答的消息 id 在内存里保存 `LoreConversation`，包括全部消息和 `SeenLines`。

- 下一问紧接在这条回答之后：带着上一问的完整对话继续，前缀缓存同样命中。
- 恢复的旧会话：从答案文本开始。

### 没有函数调用的 provider

请求带 `tools` 时，如果返回 400/422 且错误信息提到 tool 或 function，就改用文本协议：

- 模型在正文中输出 `` ```tool {"name":…,"arguments":…}``` ``；
- 工具结果以“工具结果”用户消息返回。

### 界面

- 工具调用显示在步骤列表和状态行，例如“第 3 轮 · 阅读 level_st_09-04.txt”。
- 正文没有工具块、长度超过 160 字时，开始当作答案流式显示。之后如果又出现工具调用，就清掉重来。
- 答案开头若是一段只讲过程的短话（“已核实，现在输出完整最终答案。”“之前 grep 显示……”），由代码去掉；带出处的段落不会被去掉。
- R17b：答案按块显示（段落、列表项、表格各一块），出处从句子里拿掉，放在该块下面缩进的证据链里：
  `故事集 → 章 → [第 a–b 行]`（`splitAnswerBlocks`，`investigation_ui.dart`）。R17d：流式时已写完的块就显示证据链，
  只有正在写的最后一块等答案完成。
- R17d：问答列表**不跟随**流式内容滚动，只在发出新问题时滚到底一次；离开底部时出现“↓”按钮。思考过程是固定高度、
  可滚动的窗口，显示全文、内部也不跟随，答案完成后保留（只在内存）。这样阅读位置上方的内容不会变高变矮。
- 强调色规则：Endfield 的信号黄只做填充和粗线；文字、图标、细边框用 `accentText`（深琥珀），实心黄底上的前景用 `onAccent`。
- （v0.10.7）模式选择已删除；输入框是 `ask_composer.dart`：一张方角卡片，随文字长到 4 行，展开键到半屏、再到全屏，高度动画 220 ms，`TextField` 不重建所以焦点和草稿保留。
- 点行号打开原文阅读页（`story_reader_page.dart`）：整章原文，滚到该行段，闪两次后保持高亮。原文从库中读出，不是模型的转述。
- `record:` 出处显示为“资料 n · 标题”，点开底部弹层看原文。答案下面折叠的出处汇总保留，里面的行号同样打开阅读页。

### 写给玩家（R17b）

提示词把“查资料”和“写答案”分开：查资料的规则不变；写答案要求用自己的话叙述，引号只留给特有称谓、术语和很短的关键原话，
正文不提表、文件名、id、说话人字段等查找过程，出处放在每条末尾，遗漏只在结尾用章节名说一两句。
提示词和工具说明里**不放任何具体人物、章节或剧情示例**，格式只用占位符（`test/core/agent/lore_agent_loop_test.dart` 守卫）。

实测（deepseek-v4-flash，不思考；指标来自 live harness 的 `proseMetrics`：去掉出处后正文中引号内字数占比、正文里库内部用语次数）：

| 问题 | 版本 | 调用 | 出处 | 引号占比 | 内部用语 | 说明 |
|---|---|---|---|---|---|---|
| 缪因是谁？ | R17 | 8 | 4 + 记录 | 10.5% | 7 | 开头“库中写作谬因” |
| 同上 | R17b 定稿前 | 8 | 7 | 10.6% | 1 | 章节用篇名；留有一段过程话（已由代码去掉）和“库中作”（已改提示词措辞） |
| 塔露拉在切尔诺伯格事件之后… | R17 | 14 | 41 | 19.8% | 0 | |
| 望做了什么？ | R17b | 34 | 71 | 15.0% | 0 | 开头直接介绍人物，按时期叙述 |

同一题的单次运行波动较大（缪因一题另有一次 61 次调用、几乎只引用资料的运行，发生在改掉“最后说明读了哪些章节”之前）。

### 答案用 JSON 输出（R17c）

只有提示词时引号仍多（15%）。R17c 让主 agent 的最终答案只输出一个 JSON 对象（`loreAnswerFormat`）：

```
{"verdict": "...",            // 只在事实核查
 "entries": [{"heading": "<小节标题>"},
             {"text": "<正文>", "cite": [["<story_id>", 起始行, 结束行], ["record", "<记录 id>"]]}],
 "coverage": "full|gaps", "gaps": "<可能遗漏的方面>"}
```

- `LoreAnswerStream`（`lore_answer_json.dart`）边收边把 JSON 转成答案 markdown：小节标题前的条目是段落，之后是列表项，
  每条的出处接在该条末尾。之后的出处核对、状态、证据链、存档都不变；模型没按 JSON 写时按原来的 markdown 处理。
  对话里保留模型自己的 JSON，追问时格式一致。子 agent 仍交回 markdown 笔记。
- 正文规则（0.14 起）：称呼、名词和关键的一两句可以照原文写，不要大段照搬台词。原来写的是“不要用引号引用台词，整句、半句都不行”，
  并由代码检查引号里的文字是否照搬、照搬就退回；真机上那次退回多花一次调用，模型只是把所有引号去掉（连被问的词本身的引号），2026-10-10 删去检查。
- 出处的故事集名、章名由代码按目录表补出，不让模型写（模型写的名字可能错）。

| 问题 | 版本 | 调用 | 出处 | 引号占比 | 引号数 | 内部用语 | 退回 |
|---|---|---|---|---|---|---|---|
| 望做了什么？ | R17b | 34 | 71 | 15.0% | 83 | 0 | — |
| 同上 | R17c | 31 | 57 | 0.5% | 9 | 0 | 0 |
| 缪因是谁？ | R17b | 8 | 7 | 10.6% | 30 | 1 | — |
| 同上 | R17c | 32 | 32 | 1.4% | 6 | 0 | 0 |

R17c 剩下的引号只是「二哥」「岁」这类称谓。缪因一题开头写作“你问的‘缪因’，在游戏里写作谬因”。

### 审稿与按阶段整理（R18）

起因（v0.10.2 真机）：概括题平铺二十多条，故事后段揭示的性质没有在开头交代，也不去其他故事求证。
开发者在“写作前先读梗概和最后几章”（固定阅读步骤）与“审稿子 agent”之间选了后者：固定步骤每题都付成本，
揭示也不一定在最后几章；审稿用新的上下文从读者角度提问，能同时发现性质、其他故事和答非所问的问题。

```
主 agent 写详细版（R17c JSON）→ 出处核对 → 审稿（1 次调用，无工具）
   ok → 整理            issues → 意见作为 user 消息追加，主 agent 回原文核实、重写 → 出处核对 → 整理
整理：答案有 ≥5 条正文时，主 agent 在原对话上再写一轮 {"stages":[{"heading","text","from":[条目号]}]}
显示：信封 + 整理版 + [DETAILS] + 详细版（折叠）
```

- **审稿**（`loreReviewPrompt`）：输入是问题、所引故事的名字和去掉出处的答案；看不到原文。只问整个故事或其他故事层面的事——
  后来的揭示是否改变了经历的性质、其他故事里是否有重要经历或可印证修正的叙述、是否答非所问；最多三个问题，没有就回 ok。
  它的了解只是线索，主 agent 收到的消息写明“只是线索，不是证据”，原文支持原答案时保持不变。每题一轮；只主 agent；
  最后一轮跳过；调用失败或回复读不出来就放行。审稿意见显示在思考窗口，审稿回复记在会话日志（`（审稿）…`）。
- **整理**（`loreStagePrompt`）：模型只写段落和每段概括的条目号；每段出处 = 这些条目出处的并集（同章重叠或相邻的行段合并），
  没被任何段覆盖的条目并入前一个被覆盖条目所在的段，所以出处一个不丢、也不会多出没核对过的出处。字数预算约为详细版正文的四分之一。
  整理失败（解析不了、条目号全无效）时只显示详细版。整理这一轮不留在对话里：追问时对话停在详细版 JSON，模型不会学着写 `stages`。
- **界面**：详细版流式时就写在折叠行“详细经过 · N 条”里（行高不变，可点开），整理版随后写在它上方；旧答案没有标记，照原样显示。
  答案下方的证据汇总只数详细版的出处。

实测（deepseek-flash，不思考，库为 v0.10.1 资产）：

| 问题 | 版本 | 调用 | 输入 token（缓存命中） | 耗时 | 出处 | 说明 |
|---|---|---|---|---|---|---|

## 4. 已知限制与后续

- **手机上的 SQL 耗时**：电脑上全表 `LIKE` 约 0.1–0.3 s，手机上还没实测（预计慢几倍，仍远低于 8 s 超时）。超时会在 SQLite 内部中止，不会在后台继续扫描。
- **单次运行的波动**：同一问题偶尔会漏掉某个阶段（R17 第一次塔露拉运行漏了 EG-7）。靠全库统计列出最多 160 个故事、模型可以拆给子 agent 来缓解；不加针对具体问题的规则。
- **成本随问题宽度增长**：跨七章的整理问题约 25 万未命中缓存的 token；窄问题 1.5–5 万。
- **答案不分层、叙述框架后知后觉**：R18 用审稿与按阶段整理处理，见上文。剩下的问题：审稿提什么有波动
  （同题一次只问后续故事、一次切中本故事的揭示）；审稿依赖模型对作品的记忆，记不得的故事它提不出问题；
  调用次数随审稿多出一截（同一数量级，按 CLAUDE.md 的成本取舍暂不处理）。

## 5. 0.14 重构（2026-10-09）

依据：v0.13.0 真机 10 个会话、16 轮问答（gemini-3-flash / gemini-3.7-flash-high 中转、glm-5.3-flash）。3 轮失败、4 轮取消，
一题 1.5–24 分钟、16–149 万输入 token；156 次工具调用里 26 次（17%）出错。骨架（一个模型、通用工具、代码核对出处）保留，改外围。

### 可靠性

- **数据库连接被别处关掉**（`database_closed`，海嗣 4 个会话）：sqflite 默认同一路径共用一个连接；知识库页读 manifest、向量卡片刷新时
  以同一路径打开再 `close()`，把问答的连接也关了，之后 grep/read_story/find 全部失败直到重启。现在临时打开一律 `singleInstance: false`，
  `GameDataKnowledgeStore` 用自己的连接，连接失效时重开，`_open()` 并发安全（同一轮并行的工具共用一次打开）。
- **并行调用被拼成 `{…}{…}`**：中转站给同一轮的两个同名调用同一个 `index`，`_StreamAccumulator` 只按 index 归并。现在同 index 不同 id 视为新调用。
- **工具调用守门**（`tool_call_gate.dart`）：粘连的参数拆成几个调用；按工具 schema 校验（JSON 对象、必填、未知参数、数字/数组读法）。
  非法调用不执行；进入对话的调用参数一律是合法 JSON（原样存非法参数曾让中转站丢掉调用、请求以模型那一轮结尾，Gemini 回 400）；
  报错写明收到了什么、缺什么、正确写法。某一轮的调用全部被拒时，一旦后面有调用成功，那一轮就不再出现在请求里。
- **空回复**：先原样重试一次，再改非流式、再改文本协议——只对这一轮；两轮都需要时才保持（`AgentTransport.stickyAfter`）。
  服务商明确拒绝工具时仍整题改用文本协议。
- **等待可见**：模型调用还没有任何输出时，每 10 s 状态行显示“等待服务商响应（已 N 秒）”；失败、超时、空回复的调用记入时间线（`llm_error:…`、`llm_empty`）。
- **取消立即生效**：`AskChatNotifier` 取消时直接断开事件流、当场记下用量（以前要等下一个事件，期间新问题会重置用量，取消的一轮记成 0）。
- **SQL 写错列**：`no such column/table` 时附上所涉表的真实列（或全部表名）。

### 检索

- **`search`**（`tools/search_tool.dart`，取代 `find`）：一次查所有已安装游戏的剧情原文（有向量服务时按整个 query 的意思检索，query 里空格分开的词
  各自做关键词检索，RRF 融合）、剧情以外的资料和 Wiki，**按来源分组**返回：每个故事的标签、story_id、语义段落前 8 行与关键词命中行。打印出的行记入
  `SeenLines`，可直接引用。某个游戏最接近的段落比另一游戏远 0.08 以上、关键词命中也不比它多时，只写一行说明并附命中数（向量检索总会返回点什么）。
- **第一批检索**：第一次模型调用前先检索一批。最初（10-09）由代码用问题原文跑一次 `search`、关键词取问题里出现的库中名字；
  10-10 改为由一次独立的小调用拟定检索词（见本节末“真机两份会话之后”），代码不再从问题里切词或找名字。没有向量时界面与工作过程提示
  “只用关键词检索，问答质量可能下降”。
- **两个游戏一视同仁**：提示词删去“先判断问题属于哪个游戏再只查那个”；`grep` 全库统计按游戏分节、各自给出总数（再旅者一题终末地的 8 行
  曾排在 154 行明日方舟结果之后被忽略）。
- **Wiki 与本地库同为检索来源**：`search` 同时给出 Wiki 页面；提示词不再规定“库里查不到才查 Wiki”，但答案仍区分来源（“据 Wiki 整理”），
  原文能印证的同时引原文，冲突时两处都写。

### 上下文与成本

- 工具结果上限 16k → 8k 字；`read_story` 默认 200 行、最多 300 行；折叠阈值 36 万 → 8 万字，最近 6 条消息不动；折叠后读过的行仍可引用。
- 追问时上一问的工具结果全部折叠（问答文本与 `SeenLines` 保留）。
- 出处核对：没读过原文的出处不超过三分之一时由代码删去，不再整篇重写（删了哪些只写进会话记录）；更多、缺行号、没有可识别的出处才退回一次。
- “整理答案”只发问题和条目（约 3 千 token），不再带整段对话。
- 审稿与子助手默认关闭（输入框“回答选项”可开；旧版保存的“复核开”不沿用）。子助手每题最多 2 个、每个 10 轮，过程转发到界面。
- 每题最多 30 轮。

### 界面

- 工作过程：`read_story` 显示故事名（以前解析 `【】`，工具输出是 `《》`，所以总退回文件名）；所有失败（错误、工具出错、参数、SQL）标红并在标题下写原因；
  子助手的步骤显示为“助手 n · …”；`search` 显示找到的篇数。答案被退回时界面只显示一行“回答格式出错，正在重新构思回答…”，不留步骤（10-10）。

### 离线检验

- 手机上的两个库 + 会话里的原问题跑预检索（`test/live/scratch/presearch_probe_test.dart`，本地）：每题 0.3–1.4 s；用库里一个向量块当查询向量
  （不调嵌入接口）检验语义路径：自身故事排第一（1.00），同活动的相关章节随后，终末地无关段落被略去。

- “整理答案”只看条目后，较弱的模型丢了语言：先写英文思考和英文版，再写中文版；旧解析从第一个 `{"stages"` 读到全文最后一个 `}` → 失败。
  提示词写明语言与条目一致、只回一个 JSON；解析按每个对象自己的闭括号切开，取最后一个可用版本。
- 会话记录：一轮的几个调用先一起宣布、输出随后，只有最后一个调用记下了输出 → 每个输出按顺序记到自己的调用。

第二轮发现并修正：
- 资料出处写成 `record:record:<id>`（`search` 把 id 显示为 `record:<id>`，模型把整串当 id）：答案正文先规范化，JSON 条目解析与界面也容忍。
- 追问的预检索带上一问（`LoreConversation.question`；恢复的会话取历史里的上一问）：两句一起做向量，名字从两句里取。
- `search` 的资料部分也查 `entity_documents`（干员档案合集：种族、履历、档案）；**记录的主体名等于关键词的排最前**（`entity_name`，3 分），
  其次标题、正文；片段取在主体名以外的关键词附近。引用弹窗在 `normalized_records` 找不到时查这张表。
  v0.12.0 的终末地资产这张表的 id 没有 `ef/`，读取时补上。
- 关键词：按标点、虚词与疑问词把问题切成短语；嵌在短语中间的名字是误命中，丢掉；没有向量（或没有名字）时短语本身也作关键词。
- 核查结论 `verdict` 是否写出取决于模型（GLM 把“这个说法对吗”当普通问答，结论写在正文里），未改。

#### 无向量时由模型定检索词（2026-10-10）

依据：评测集 33 题（29 题有金标）在无向量时，用代码定的关键词（库里的名字 + 按虚词切出的短语）做预检索，前 5 篇里有金标故事的只有 16/29 题、金标故事 23/54 篇
（本地探针 `test/live/scratch/eval_presearch_probe_test.dart`，不花钱）。失败多因没有分词：切出“龙门相撞”“死负责”这种原文里不会出现的短语、
单字名字不算、名字被并进长短语；同义说法与游戏里的叫法只有模型知道（项目原则：场景知识交给 Agent）。实测里预检索之后模型无一例外又自己检索了 2–4 次。

改动：
- 没有向量（未配置、库里没有、模型不一致）时**不做预检索**：模型第一轮自己调 `search`；工作过程照常提示“问答质量可能下降”。有向量时不变。
- 这时 `search` 的说明换成字面匹配版：写原文里会出现的词（叫法、别称），空格分隔，不写整句；系统提示的“工作方式”两种情况都写到。
- 结果开头列出每个关键词命中多少行，0 行的标“原文里没有这个写法”；一次最多 8 个词（与查询上限一致，原来悄悄只用前 6 个），多出的列为“未使用”。
- Wiki 查询词改用实际关键词（原来用未过滤的名字，曾搜了“比利”）；“名字嵌在短语中间就丢掉”只对两个字的名字生效（曾把“导致特蕾西娅死亡”里的名字丢掉）。

#### 真机两份会话之后（2026-10-10）

依据：开发者在手机上（GLM，有向量，带桥的本地构建）问的两个会话、四个问答。发现与改动：

| 看到的 | 原因 | 改动 |
|---|---|---|
| 答案完整，却标成“资料未覆盖” | 模型最后一轮用散文作答、出处只写了故事名；没有出处的散文答案不退回，直接判 not_covered | 读过资料却一条出处都没有的答案（JSON 或散文）退回一次 |
| 三处正确的出处被整条删掉，对应段落没有出处 | 检索只列了一段里的几行（如 L103、L105），答案引 103-105，核对要求范围内每一行都展示过 | 范围只读过一部分时裁成读过的那几段；`search` 不再把没列出的行写成“这一段到 L…” |
| 追问的 8 个关键词里 7 个是上一问的 | 上一问与本问合并检索，上一问排在前面，一次只取 8 个 | 见下“第一批检索” |
| 关键词是句子碎片（“伊比利亚那里”“大静谧又不”） | 问题里没有库中名字时按虚词切短语 | 同上；`phrasesOf`、虚词表、`namesOccurringIn` 删除 |
| PRTS 每次都“没有相关页面” | Wiki 检索词是前两个关键词拼在一起 | Wiki 词由拟定检索的调用单独给；模型自己的 `search` 默认用第一个词，可用 `wiki` 参数指定 |
| 明日方舟的问题里三分之一是终末地内容 | 任何关键词命中都让“意思较远就略去”失效，泛词总会命中 | 意思明显较远、关键词命中也不比另一游戏多时只列一行（附命中数） |
| 泛词带出无关资料 | 资料按命中的字段打分，平分时取最长的 | 每个词按它在剧情里出现的行数降权 |
| 一次退回多花 9.5 秒，只是把引号全去掉 | “照搬台词”的代码检查 | 删去检查；提示词改为“不要大段照搬” |
| 引的是上一问读过、已折叠的行，内容张冠李戴 | 折叠后行号仍可引用，原文已不在对话里 | 折叠处写明它展示过哪些行段，并说明要用先重读 |
| 记录里看不出为什么退回 | 退回原因只发给界面 | 原因、被裁和被删的出处写进会话记录（`recordNote` 事件） |

**第一批检索由独立的调用拟定**（`search_planner.dart`，提示词 `loreSearchPlanPrompt`）：

- 输入：`search` 工具自己的说明（同一份文字）、问题；追问时加上一问和上一答的开头与小节标题。输出一个 JSON：最多三条检索词（空格分隔的词）和一个 Wiki 词。
- 代码并行执行这些检索，作为普通的 `search` 调用和结果加入对话（和模型自己的调用一样可折叠）；用户消息只有问题本身（以前预检索结果贴在问题后面，永不折叠，每追问一次多留四五千字）。
- 用不带思考的 client，超过 25 秒不等。写不出来时：有向量就用问题原文按意思检索一次；没有向量由主模型第一轮自己检索。有无向量走同一条路。
- `search` 的关键词只是 query 里空格分开的词（单独一个不超过 8 个字的词也算）；整句只按意思检索。Wiki 请求与读库同时进行。
- 记录：会话里这一步的原始回复记为“（拟定检索）…”，之后每条检索各一条记录。

**退回 = 整轮回档**（开发者要求：出错的回答不进上下文、不在界面保留）：

- 被退回的回答不加入对话；重问时附一条说明（哪里不对：没有可识别的出处 / 哪些出处没读过 / 哪些缺行号），答案被接受后这条说明从对话里拿掉，追问时看不到。
- 界面：清掉已流出的答案和这一轮的思考，状态行显示“回答格式出错，正在重新构思回答…”，工作过程不留步骤；答案里也不再写“已删去 N 处”。
- 重写仍不合格时用第一份回答（留在内存里）经代码处理后给出。审稿退回（默认关）不变：它要让主模型看到原答案和读者的问题。

**“已读”是一本账**（`SeenLines`）：行只有连同正文展示才算；`sql` 不选 `content` 不算，`id` 只在查 `normalized_records` / `entity_documents` 时算记录；`search` 列出的资料记为片段（可引用，结果里写明）；
每次工具调用展示了什么另记一份，折叠时写进指引。

**提示词按角色组合**（`loreRolePrompt`：answer / helper / planner / reviewer / stager）：出处的种类只在 `loreCitationRules` 一处，JSON 里怎么写只在 `loreCiteShape` 一句
（答案格式与退回说明共用）；`search` 做什么只在工具说明里；开场白与审稿提示词按已安装的游戏写；顺序是 能读什么 → 怎么工作 → 能引用什么 → 怎么写。
中途说的话（轮数上限、请继续、退回说明）也在提示词文件里，受同一个守卫测试。

验证：全量测试与 analyze 通过；上表每一行有对应的离线用例（`lore_agent_loop_test.dart`、`story_vectors_test.dart`、`multi_game_retrieval_test.dart`、`agent_provider_test.dart`）。
**这些改动之后没有用真实模型或真机再跑**（要花钱、要开发者在场）：拟定的检索词好不好、整轮耗时有没有下降，都还没有数据。
