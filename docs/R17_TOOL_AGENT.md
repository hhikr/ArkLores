# R17：工具型剧情 Agent（一个模型 + 通用工具 + 只追加的对话）

> 状态：v0.10.1 起是剧情问答**唯一**的流程。R13–R16 的分步流程（`PlannerLoop`、状态、提取器、writer）已删除，
> 原文和逐步说明（`ASK_PIPELINE_FLOW.md`）都在 git 历史中。

## 1. 为什么改

用户让几个通用 agent 直接读 GameData 库回答剧情问题，它们都只拿到一句很简单的提示词：

- deepseek-harness：不思考、不思考加子 agent、低档思考三档；
- 两个匿名 agent。

问题是“塔露拉在切尔诺伯格事件之后做了哪些事情？”，日志在 `logs/成熟的agent如何处理/`。

结果它们全都比 R13–R16 的分步流程好。R13–R16 补丁越打越多，样例问题变好了，别的问题和追问反而变差。

读日志后发现，这些 agent 的做法几乎一样：

1. **先看全局。** 用一条聚合 SQL 拿到全语料的地图：含某个名字的行按 `story_id` 分组计数，关联 `story_catalog` 按顺序排。不需要猜 story_id。
2. **整章读，章内搜。** 把整章导出，再在章内 grep 或按偏移读，一次 8–16k 字。
3. **读原文的模型就是写答案的模型。** 没有摘要器，也没有 writer 从材料里选段落。
4. **对话只追加、不重排。** 所以 97% 的输入命中前缀缓存：DSH 不思考档新增 7.5 万 token，缓存命中 214 万。
5. **没有手写的进度规则。** 不设预算，没有重读阶梯，不做复核。由模型自己判断还缺什么。

R16 正好相反：

- 决策器只看压缩后的状态；
- 原文先变成摘要，再由 writer 从 6 万字里选材；
- 每步重建提示词，缓存失效。

结果是贵，信息还在一道道交接中丢失。补丁之所以只对样例有效，原因就在这个结构上。

## 2. 结构

```
用户问题 ─► AskChatNotifier ─► (auto: QuestionRouter 选 AnswerStyle)
            ─► StoryQaAgent.run ─► LoreAgentLoop
                 system: loreSystemPrompt(style)（库结构说明 + 工作方式 + 引用格式 + 输出格式）
                 messages: [上一问的完整对话（追问时）] + 用户问题 + 每轮 assistant/tool 消息（只追加）
                 每轮：client.streamTurn(messages, tools) ─► 文本增量 / tool_calls
                       有 tool_calls → 同一轮的调用并发执行（delegate 即并行的子 agent），结果按顺序原样追加
                       没有 → 最终答案 → 出处核对（最多退回一次）→ 状态信封
```

| 文件 | 作用 |
|---|---|
| `lib/core/agent/lore_agent_loop.dart` | 循环、文本协议回退、上下文折叠、出处核对、状态 |
| `lib/core/agent/lore_tools.dart` | 工具；`SeenLines` 记录本次给模型看过的行和记录 |
| `lib/core/agent/lore_agent_prompts.dart` | 系统提示（所有问题同一份，R13） |
| `lib/core/gamedata/readonly_sql.dart` | 只读 SQL：语句检查，每次查询一个后台 isolate，超时用 `sqlite3_interrupt` 中止 |
| `lib/core/llm/openai_client.dart` | `streamTurn`：SSE 中按 index 拼接 `tool_calls` |

### 工具

| 工具 | 作用 | 上限 |
|---|---|---|
| `sql(query)` | 一条只读 `SELECT`/`WITH` | 200 行 / 16k 字，8 s 超时 |
| `grep(pattern, story_ids?/collection?, context, max_hits)` | 子串匹配，`\|` 表示任一。不给范围：全库按故事统计行数（主线在前，其余按上线时间）；给范围：命中行加上下文，命中行标 `*` | 150 行，列出 160 个故事 |
| `read_story(story_id, start, count)` | 连续读原文，`L行号 [说话人] 内容` | 500 行 / 16k 字 |
| `find(query, collection?)` | 按意思找：FTS 关键词，配置了向量 API 时再融合语义召回（复用 R12 `SearchStoryLinesTool`）；只是定位线索 | 6 个故事 |
| `outline(collection)` | 故事集章节、关卡号、官方梗概（只用于定位） | 16k 字 |
| `similar_names(name)` | 读音或字形相近的名字（R15 `name_similarity`） | 8 个 |
| `delegate(task, story_ids?, collection?)` | 把一部分阅读交给子 agent（只主 agent 有） | 子 agent 20 轮 |

### 子 agent

`delegate` 启动一个新的 `LoreAgentLoop`（`subtask: true`）：

- 有自己的对话，工具与主 agent 相同，但没有 `delegate`（只有一层）；
- 系统提示要求只完成交给它的查找，最后交回带出处的要点；它也走自己的出处核对；
- 结束后它看过的行和记录并入主 agent 的 `SeenLines`，所以主 agent 可以直接引用它交回的出处；
- 同一轮的多个调用并发执行，事件和 tool 消息仍按调用顺序给出。

是否拆分由模型决定。实测：读二十章左右的问题它自己读完；“凯尔希在第 9–15 章的主要行动”派出了 5 个子 agent。

### 写错的名字

缪因、切尔诺贝利这类写错的名字，没有专门的匹配代码，靠三件事解决：

1. 提示词允许模型用自己对作品的了解**构造查询**，但这些了解不能当证据。
2. 0 命中会如实写“0 行”，并要求先换写法再下结论。
3. `sql`、`grep` 零命中时自动附上 `similar_names` 的提示。

实测效果：

- 切尔诺贝利 → 切尔诺伯格（剧情提及 374 次）；
- 缪因 → 谬因（干员）。

答案用原文写法，第一次提到时括号注明用户的写法：“X（你写的是 Y）”（R17b 起；之前是开头写“库中写作 X”）。

### 出处

- 剧情台词：`story_id:起始行-结束行`。行号是 `line_index`，从 0 开始。
- 其他资料（`normalized_records`）：`record:<id>`。

核对规则：

- 行号范围里的每一行都必须由工具给模型看过。`read_story` 的页面、`grep` 的命中和上下文、`sql` 结果中带 `story_id + line_index` 的行都算。
- 记录 id 必须出现在某次 `sql` 结果里。
- 只写文件名、没有行号的出处也会被退回。
- 每个问题最多退回一次；仍无法核实的出处会附注在答案末尾。

### 状态信封

- **not_covered**：没有任何核实过的出处。
- **partial**：模型自己写了 `[COVERAGE: gaps]`，或者到了轮数上限。
- **answered**：其余情况。

### 安全阀

只有下面几个，不设预算提示，不拒绝重读，也不做复核：

- 每问最多 60 轮，最后一轮 `tool_choice: none`，要求直接作答；
- 只读 SQL 超过 8 秒，用 `sqlite3_interrupt` 在 SQLite 内部中止语句（工作 isolate 在主 isolate 允许前不关闭连接，所以中止不会碰到已释放的连接），并告诉模型缩小范围；
- 上下文超过 36 万字时，把最早的工具结果折叠成一行指引，最近 8 条消息不动；
- 用户可以随时停止。

### 追问

`AskChatNotifier` 按回答的消息 id 在内存里保存 `LoreConversation`，包括全部消息和 `SeenLines`。

- 下一问紧接在这条回答之后：带着上一问的完整对话继续，前缀缓存同样命中。
- 恢复的旧会话：从答案文本开始。

### 没有函数调用的 provider

请求带 `tools` 时，如果返回 400/422 且错误信息提到 tool 或 function，就改用文本协议：

- 模型在正文中输出 `` ```tool {"name":…,"arguments":…}``` ``；
- 工具结果以“工具结果”用户消息返回。

### 界面

- 工具调用显示在步骤列表和状态行，例如“第 3 轮 · 阅读 level_st_09-04.txt”。
- 正文没有工具块、长度超过 160 字时，开始当作答案流式显示。之后如果又出现工具调用，就清掉重来。
- 答案开头若是一段只讲过程的短话（“已核实，现在输出完整最终答案。”“之前 grep 显示……”），由代码去掉；带出处的段落不会被去掉。
- R17b：答案按块显示（段落、列表项、表格各一块），出处从句子里拿掉，放在该块下面缩进的证据链里：
  `故事集 → 章 → [第 a–b 行]`（`splitAnswerBlocks`，`investigation_ui.dart`）。流式时只显示正文，答案完成后出现证据链。
- 点行号打开原文阅读页（`story_reader_page.dart`）：整章原文，滚到该行段，闪两次后保持高亮。原文从库中读出，不是模型的转述。
- `record:` 出处显示为“资料 n · 标题”，点开底部弹层看原文。答案下面折叠的出处汇总保留，里面的行号同样打开阅读页。

### 写给玩家（R17b）

提示词把“查资料”和“写答案”分开：查资料的规则不变；写答案要求用自己的话叙述，引号只留给特有称谓、术语和很短的关键原话，
正文不提表、文件名、id、说话人字段等查找过程，出处放在每条末尾，遗漏只在结尾用章节名说一两句。
提示词和工具说明里**不放任何具体人物、章节或剧情示例**，格式只用占位符（`test/lore_agent_test.dart` 守卫）。

实测（deepseek-v4-flash，不思考；指标来自 live harness 的 `proseMetrics`：去掉出处后正文中引号内字数占比、正文里库内部用语次数）：

| 问题 | 版本 | 调用 | 出处 | 引号占比 | 内部用语 | 说明 |
|---|---|---|---|---|---|---|
| 缪因是谁？ | R17 | 8 | 4 + 记录 | 10.5% | 7 | 开头“库中写作谬因” |
| 同上 | R17b 定稿前 | 8 | 7 | 10.6% | 1 | 章节用篇名；留有一段过程话（已由代码去掉）和“库中作”（已改提示词措辞） |
| 塔露拉在切尔诺伯格事件之后… | R17 | 14 | 41 | 19.8% | 0 | |
| 望做了什么？ | R17b | 34 | 71 | 15.0% | 0 | 开头直接介绍人物，按时期叙述 |

同一题的单次运行波动较大（缪因一题另有一次 61 次调用、几乎只引用资料的运行，发生在改掉“最后说明读了哪些章节”之前）。

### 答案用 JSON 输出（R17c）

只有提示词时引号仍多（15%）。R17c 让主 agent 的最终答案只输出一个 JSON 对象（`loreAnswerFormat`）：

```
{"verdict": "...",            // 只在事实核查
 "entries": [{"heading": "<小节标题>"},
             {"text": "<正文>", "cite": [["<story_id>", 起始行, 结束行], ["record", "<记录 id>"]]}],
 "coverage": "full|gaps", "gaps": "<可能遗漏的方面>"}
```

- `LoreAnswerStream`（`lore_answer_json.dart`）边收边把 JSON 转成答案 markdown：小节标题前的条目是段落，之后是列表项，
  每条的出处接在该条末尾。之后的出处核对、状态、证据链、存档都不变；模型没按 JSON 写时按原来的 markdown 处理。
  对话里保留模型自己的 JSON，追问时格式一致。子 agent 仍交回 markdown 笔记。
- 正文规则只写“不要用引号引用台词，整句、半句都不行，一律转述”，**不写**“哪些可以加引号”（写了模型会刻意去用）。
- 代码检查：引号里的文字（去掉标点后 ≥5 字）与所引行原文逐字或二元组 ≥70% 相同，视为照搬台词，和出处问题合用那一次退回。
- 出处的故事集名、章名由代码按目录表补出，不让模型写（模型写的名字可能错）。

| 问题 | 版本 | 调用 | 出处 | 引号占比 | 引号数 | 内部用语 | 退回 |
|---|---|---|---|---|---|---|---|
| 望做了什么？ | R17b | 34 | 71 | 15.0% | 83 | 0 | — |
| 同上 | R17c | 31 | 57 | 0.5% | 9 | 0 | 0 |
| 缪因是谁？ | R17b | 8 | 7 | 10.6% | 30 | 1 | — |
| 同上 | R17c | 32 | 32 | 1.4% | 6 | 0 | 0 |

## 4. 已知限制与后续

- **手机上的 SQL 耗时**：电脑上全表 `LIKE` 约 0.1–0.3 s，手机上还没实测（预计慢几倍，仍远低于 8 s 超时）。超时会在 SQLite 内部中止，不会在后台继续扫描。
- **单次运行的波动**：同一问题偶尔会漏掉某个阶段（R17 第一次塔露拉运行漏了 EG-7）。靠全库统计列出最多 160 个故事、模型可以拆给子 agent 来缓解；不加针对具体问题的规则。
- **成本随问题宽度增长**：跨七章的整理问题约 25 万未命中缓存的 token；窄问题 1.5–5 万。
