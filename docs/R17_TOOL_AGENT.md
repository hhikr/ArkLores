# 工具型剧情 Agent（一个模型 + 通用工具 + 只追加的对话）

> 状态：v0.10.1 起是剧情问答**唯一**的流程（代号 R17）；0.14 重做了它外围的检索、可靠性和界面，骨架没有变。
> 这份文档写的是 v0.14.0 的样子。逐轮的改动经过、每一次验收的原始表格在 git 历史里（`git log -- docs/R17_TOOL_AGENT.md`），
> 面向用户的变化在 `CHANGELOG.md`，仍开放的问题在 `KNOWN_LIMITATIONS_AND_DEBT.md` §7。

## 1. 为什么是这个结构

v0.10 之前的问答是分步流程（决策器看压缩后的状态 → 原文先变摘要 → writer 从材料里选段落，每步重建提示词）。
开发者让几个通用 agent 只凭一句提示词直接读库回答同一个问题，结果全都比分步流程好。它们的做法几乎一样：

1. 先看全局：一条聚合查询拿到某个名字在全库的分布，不猜 story_id。
2. 整章读、章内搜。
3. 读原文的模型就是写答案的模型，中间没有摘要器。
4. 对话只追加、不重排，所以绝大部分输入命中前缀缓存。
5. 没有手写的进度规则（预算、重读阶梯、复核），由模型自己判断还缺什么。

分步流程贵，信息还在一道道交接里丢；补丁只对样例有效，原因就在结构上。所以改成：一个模型、通用工具、只追加的对话，代码只负责核对出处。

## 2. 一次问答怎么走

```
用户问题 ─► AskChatNotifier ─► StoryQaAgent.run ─► LoreAgentLoop
   第一批查找：一次独立的小调用按问题拟定（search / outline / wiki_search），代码执行，作为普通的调用和结果进入对话
   system: loreSystemPrompt()（资料来源概览 + 工作方式 + 阅读原则 + 出处格式 + 答案格式）
   messages: [上一问的对话，工具结果已折叠（追问时）] + 用户问题 + 每轮 assistant/tool 消息（只追加）
   每轮：client.streamTurn(messages, tools) ─► 文本增量 / tool_calls
         有 tool_calls → 守门（拆分粘连、按 schema 校验）→ 同一轮的调用并发执行，结果按顺序追加
         没有 → 最终答案（JSON）→ 出处核对 → 状态信封
```

| 文件 | 作用 |
|---|---|
| `lib/core/agent/lore_agent_loop.dart` | 循环、文本协议回退、上下文折叠、出处核对、状态 |
| `lib/core/agent/lore_tools.dart`、`lib/core/agent/tools/search_tool.dart`、`lib/core/agent/tools/wiki_tools.dart` | 工具；`SeenLines` 是唯一的“已读”账本 |
| `lib/core/agent/tool_call_gate.dart` | 工具调用守门 |
| `lib/core/agent/search_planner.dart` | 拟定第一批查找 |
| `lib/core/agent/lore_agent_prompts.dart`、`lore_endfield_prompts.dart` | 提示词，按角色组合（`loreRolePrompt`：作答 / 子助手 / 拟定 / 审稿 / 整理） |
| `lib/core/agent/lore_answer_json.dart`、`lore_answer_stages.dart` | 答案 JSON → markdown；按阶段整理 |
| `lib/core/gamedata/readonly_sql.dart` | 只读 SQL：语句检查，后台 isolate，超时用 `sqlite3_interrupt` 中止 |
| `lib/core/llm/openai_client.dart` | `streamTurn`：SSE 中拼接 `tool_calls`（同 index 不同 id 视为新调用） |

## 3. 工具

所有工具的结果上限 8k 字。检索面是 `MultiGameRetrieval`：装了几个游戏的库就查几个，终末地的 id 以 `ef/` 开头。

| 工具 | 作用 |
|---|---|
| `search(query?, near?, collection?, game?, wiki?)` | 统一检索。`query` 按意思检索（有向量服务时）并把空格分开的词各自做关键词检索，RRF 融合；同时查剧情、剧情以外的资料和 Wiki，**按来源分组**返回。打印出的行记为已读，可直接引用 |
| `read_story(story_id, start, count)` | 连续读剧情原文，`L行号 [说话人] 内容`；默认 200 行、最多 300 行 |
| `read_record(id)` | 读剧情以外的资料（档案、语音、描述），两张表都找，分页；开头写所属对象 |
| `grep(pattern, story_ids?/collection?, context, max_hits, game?)` | 子串匹配，`\|` 表示任一。不给范围：全库按故事统计行数；给范围：命中行加上下文，命中行标 `*` |
| `sql(query, game?)` | 一条只读 `SELECT`/`WITH`，200 行，8 秒超时。用来统计和按条件找，不用来翻页读长文 |
| `guide()` | 知识库手册：表与列、绑定、资料页结构、终末地库的结构 |
| `outline(collection)` | 故事集的章节、关卡号、官方梗概；末尾是相关的故事集 |
| `similar_names(name)` | 读音或字形相近的名字 |
| `wiki_search(query, game?, limit?)`、`wiki_read(page, game?, start, count, section?)` | 开着“Wiki 资料”时才有（`WIKI_EVIDENCE.md`） |
| `delegate(task, story_ids?, collection?)` | 开着“子助手”时主 agent 才有：把一部分阅读交给子 agent |

几条设计上的规矩（原因都来自真实会话）：

- **`search` 的分布与“各给一段”**：结果开头每个词一行，写它在哪几部故事集里各有多少行（`computeTermSpread`：列到八成或 6 部，
  补最多 2 部“占比高的”短篇，写出其余的占比）；分布里列出、最相关的 5 篇没覆盖的故事集，各给一段原文（`_elsewhere`，每个游戏最多 6 段、共 3500 字，较少见的词先取）。
  只写“在哪”时，模型有一半的时候读完最相关的一篇就作答；能确定地取到的原文由工具直接给，不靠模型去要。
  分布只是定位线索、不算已读；所有词同一个格式，不按词的种类分支。
- **`near`**：写一段读过的剧情的位置（`<story_id>:<行号>`），用库里已有的向量找别的故事集里相近 0.70 以上的段落（每部一段、最多 5 段），不调嵌入服务。
  `query` / `near` 至少给一个（`AgentTool.requireOneOf`）。真实模型至今没有主动调用过它。
- **较远的游戏只列一行**：某个游戏最接近的段落比另一游戏远 0.08 以上、关键词命中也不比它多时，只写一行说明和命中数。
- **相关的故事集**（`outline` 末尾）：共有说话人（两边各 10 行以上）与剧情向量的故事集平均方向按名次融合，前 6 个，现算不加表。
  库里没有数据能说明故事之间谁承接谁，它只是线索。
- **手册不进提示词**：表结构只有查表时用得上，放在 `guide` 里，没看过时随一次问答的第一条 `sql` 结果附上（`LibraryManual`）。
- **“只列出一部分”要说剩下的在哪**：`grep` 截断或篇幅已满时列出没列出的命中在哪些故事、各几处（最多 12 个）；
  同时给了 `story_ids` 和 `collection` 时以 `story_ids` 为准。
- **指路模型不照做、工具自己能做的，由工具做**：`wiki_search` 几个词没有结果时自己把前 3 个词各搜一次。
  同一个站点同一个词的搜索合并成一次请求（进行中的和 30 分钟内问过的共用），`search` 等 Wiki 最多 8 秒。
- **0 行如实说**，并对“名字”给近似名提示：库里有完全相同的名字时不提示；类别、id 片段不算名字。找不到故事集时写明主线章节的写法（`main_<章号>`）和“可能还没收录”。
- **凡是“属于谁”的信息按表里的 id 给出**（语音的所属干员、资料的所属对象），不让模型按内容猜。

### 第一批查找

第一次模型调用之前，一次独立的小调用（`loreSearchPlanPrompt`，思考关，最多等 25 秒）只看问题（追问时加上一问和上一答的要点）和各工具自己的说明，
写出最多三条检索词、最多两个要看目录的故事集、最多两个 Wiki 搜索词（合计不超过四步）和一个附在第一条检索上的 Wiki 词。代码照着执行。
没拟定出来时：有向量就用问题原文按意思检索一次；没有向量就由主模型自己检索。**代码不从问题里切词、找名字**（切出来的是句子碎片）。

### 守门

进入对话的调用参数必须是合法 JSON：粘连的参数拆成几个调用，按工具的 schema 校验（必填、未知参数、数字与数组的读法、`requireOneOf`）。
非法调用不执行，报错写明收到了什么、缺什么、正确写法；模型的原始参数不原样存进历史（曾让一个服务商拒绝整题）。
某一轮的调用全部被拒时，一旦后面有调用成功，那一轮不再出现在请求里。

### 没有结果的查找

唯一一条手写的进度规则（开发者 2026-10-11 要的）：一个工具在一次问答里没有结果满 6 次（`maxFailedLookups`；结果以“0 行”“没有”“错误”等开头），之后不再执行。
全是空结果的一轮在模型回复过一次之后不留在上下文里（`emptyTurns`），次数旁边留下试过的调用的简短清单。对所有工具、所有问题一样。
其余仍不加：预算提示、重读拒绝、阅读计划。

### 子 agent

`delegate` 启动一个新的 `LoreAgentLoop`（`subtask: true`）：自己的对话、同样的工具但没有 `delegate`、最多 10 轮；每题最多 2 个；
它交回带出处的要点，看过的行并入主 agent 的 `SeenLines`。默认关闭。

## 4. 出处

- 剧情：`story_id:起始行-结束行`（`line_index`，从 0 起）；资料：`record:<id>`；Wiki：`wiki:<站点>:<页面>@<版本>:起始段-结束段`。
- 必须是工具连同正文给模型看过的（`SeenLines`）：`read_story` 的页面、`grep` 的命中和上下文、`search` 列出的行与资料片段、
  带 `story_id + line_index + content` 的 `sql` 结果、`read_record` 与 `wiki_read` 展示的内容。新工具一律经它登记。
- 范围只有一部分读过时，代码把出处裁成读过的那几段；没读过的出处不超过三分之一时由代码删去。
- 多数出处没读过、只有文件名没有行号、读过资料却一条出处都没有、JSON 提前闭合而后面还有条目读不到——整轮退回一次：
  被退回的答案不进对话、不显示，原因写进会话记录并作为“记录：…”一行出现在工作过程里；重问时附的说明在答案被接受后拿掉。仍无法核实的出处附注在答案末尾。
- 代码查的是“看没看过”，不查这些行是否支持那句话。

### 状态信封

- **not_covered**：没有任何核实过的出处（代码定）。
- **partial**：模型在答案里写了 `"coverage": "gaps"`，或到了轮数上限。
- **answered**：其余。

answered / partial 取决于模型自己有没有声明遗漏，代码不核对。同一道按人物问的题的 16 次运行里，改前的 4 次全是 answered、其中 3 次漏了两部没有声明；
partial 的 2 次覆盖都不差。**不要拿 answered 的比例当质量指标**；比较两版代码看答案里有出处的故事集，以及出处是不是讲这件事的行。

## 5. 答案

主 agent 的最终答案只输出一个 JSON 对象（`loreAnswerFormat`）：

```
{"verdict": "...",            // 只在核查某个说法时
 "entries": [{"heading": "<小节标题>"},
             {"text": "<正文>", "cite": [["<story_id>", 起始行, 结束行], ["record", "<记录 id>"]]}],
 "coverage": "full|gaps", "gaps": "<可能遗漏的方面>"}
```

- `LoreAnswerStream` 边收边转成 markdown：小节标题前的条目是段落，之后是列表项，出处接在每条末尾。故事集名、章名由代码按目录补出。
- 解析器对常见变体容错：平铺的 `cite`、`L97` / `97-127` 写法、漏写 `.txt`、`record:record:`；中途多了括号提前闭合的接着读同一个数组；
  字符串里没转义的引号按后文判断（只有接着 `}` 或 `, "<键>":` 才是结束）；一次回复里有几份答案时取最后一份完整的。
  模型没按 JSON 写时按 markdown 处理，只装着出处的括号读成反引号的写法。丢掉的出处计数并退回一次。
- 写给玩家：用自己的话叙述，正文不提库、表、文件名、id；称呼、名词和关键的一两句可以照原文写，不要大段照搬。用提问的语言写。
- 写错的名字没有专门的匹配代码：模型可以用自己对作品的了解构造查询（不能当证据），0 行时有近似名提示；答案用原文写法，第一次提到时注明用户的写法。
- 提示词与工具说明里不放任何具体人物、章节、活动或剧情手法，格式只用占位符（守卫测试）；凡是代码要严格解析的格式都给完整骨架。

### 提要与复核

两者不在一次提问里运行，是答案下方的按钮（`AskChatNotifier.digestAnswer` / `reviewAnswer`），只对本次运行期间的答案有。

- **提要**（5 条以上条目的答案）：模型只写段落和每段概括的条目号（`{"stages":[{"heading","text","from":[…]}]}`），每段的出处是这些条目出处的并集，
  所以出处一个不丢、也不多。只发问题和条目，不带整段对话。段数只软性提示。
- **复核**（只对最后一条）：另一次调用以读者身份、看不到原文，只问故事层面的事（后来的揭示是否改变了经历的性质、其他故事里有没有重要经历、是否答非所问），
  最多三个问题。没有问题就说明；有问题时走同一条流程的追问，原答案不动。它的了解只是线索，结论由主 agent 读原文决定。

## 6. 安全阀与兼容

- 每问最多 30 轮。最后一轮附一条“轮数已到、直接作答”的说明（`loreTurnLimitNote`），接受 `tool_choice` 的服务商另发 `none`（智谱不接受、不发），
  这一轮的工具调用不执行；只读 SQL 超过 8 秒在 SQLite 内部中止。
- 上下文超过 8 万字时把最早的工具结果折叠成一行指引（写明它展示过哪些行段、内容要用先重读），最近 6 条消息不动；追问时上一问的工具结果全部折叠。
- 追问：`AskChatNotifier` 按回答的消息 id 在内存里保存对话和 `SeenLines`，下一问接着同一段对话；从历史恢复的会话从答案文本开始。
- 空回复：先原样重试一次，再改非流式、再改文本协议——只对这一轮；连续两轮都需要才保持。服务商明确拒绝 `tools` 时整题改用文本协议
  （模型在正文里写 `` ```tool {…}``` ``）。
- 模型调用没有任何输出时，状态行每 10 秒显示已等待多久；取消立即断开事件流并记下用量。
- 知识库的数据库连接是问答自己的（别处临时打开再关闭不会连带关掉它），失效时重开。
- 思考档位每个角色显式指定，默认全部关，“深度思考”= low（各家参数见 `LLM_PROVIDERS.md`）。

## 7. 界面

- **工作过程**（答案上方，默认折叠；`work_steps.dart` + `chat_bubble.dart`）照会话记录的样子写：每一步是序号、工具名、模型写的参数原文、
  结果的计数和字数，加标记（拟定 / 重复 / 没有结果 / 出错 / 未执行 / Wiki 超时 / 助手 n）；点开是完整的参数和结果（限高、可滚动、可选中）。
  代码对答案做的事（退回、出处裁剪、删去出处、向量服务出错）是“记录：…”行。汇总行“查阅 N 次 · 读了 N 篇原文”数的是全部调用和展示过正文的故事。
- 答案按块显示，出处从句子里拿掉，放在该块下面的证据链里（故事集 → 章 → 行段）；点行号打开原文阅读页并高亮；`record:` 与 Wiki 出处点开看原文或快照。
- 问答列表不跟随流式内容滚动；思考过程是固定高度的窗口；阅读位置上方的内容在流式中不变高。
- 输入框只有一个选项按钮，面板不取焦点（键盘不动）：Wiki 资料 / 子助手 / 深度思考。
- 没有向量服务时提示“只用关键词检索，问答质量可能下降”。

## 8. 验收数据（摘要）

**替换分步流程时**（2026-10-03，deepseek-flash，不思考）：同一题调用 35–39 次 → 11 次，未命中缓存的输入降到原来的 1/5 到 1/10，耗时减半，金标章节全读。

**0.14 的依据与结果**：

- 依据：v0.13.0 真机 10 个会话、16 轮问答——3 轮失败、4 轮取消，一题 1.5–24 分钟、16–149 万输入，156 次工具调用里 26 次出错。
- 真机 17 题（2026-10-10，GLM，带桥的包）：全部答完；退回与出处裁剪都在真机上触发过。
- 拟定检索词：评测集 29 题里 25 题至少列出一篇金标（带向量）；代码从问题里切词的旧做法是 16/29。
- 按人物问的一道题，同一份代码各跑 4 次，五部故事都讲到的次数：改前 1/4，只写分布 2/4，“各给一段”之后 4/4；代价是输入约 2–3 倍（5–15 万）。
  单次运行说明不了问题，比较两版代码要两边各跑几次。
- 要查表的一道题：库里查不到要的条目时 31 次调用、47 万输入；加了没有结果的查找的上限后 13 次；库修正（复刻活动的关卡）之后 6 次 / 10.8 万查出全部 25 种敌人。

**历史问题集**（2026-10-11）：玩家在手机上实际问过的 52 份会话整理成 37 问（`test/fixtures/history_questions_eval.json`，同一个 `session` 的题是一次对话的连续几轮），
电脑上同一条 `askChatProvider` 链路、GLM、Wiki 开、两个库：全部答完，47 分 39 秒，输入 516.6 万（缓存 377.6 万），answered 28、partial 9。
同一批问题在 v0.13.0 真机上出过的失败、几十步、上百万输入这次都没有出现。它查出并已改掉的问题：

| 现象 | 处理 |
|---|---|
| 答案 JSON 里没转义的引号把每一条在第一个引号处截断（一份答案只剩两成，状态仍是 completed） | 引号按后文判断是不是结束 |
| `grep` 同时给 `story_ids` 和 `collection` 时范围被并成整部故事集 | 以 `story_ids` 为准 |
| 一份答案不是 JSON，出处写在括号里、文件名露在正文 | 括号里的出处读成正常出处 |
| `wiki_search` 多个词没有结果，模型换一组词再搜，6 次用完上限 | 工具自己逐词搜 |
| `grep` 截断后没法往后看，同一条调用原样重复 | 列出没列出的命中在哪 |
| 检索结果里 Wiki 频繁超时，占了第一步三分之一的时间 | 同一个词合并成一次请求；等 Wiki 的上限 12 → 8 秒 |
| 库里没有的人物：如实说没查到的答案被退回，重写时引无关内容凑出处 | 退回的说明写明“确实没查到就照实说” |

## 9. 试过、不要再试的

- 读资料时按向量指向相关剧情、读剧情时自动附上相近的段落：模型不用，只是加长结果。
- 由代码从问题里切词、找名字做第一批检索：切出来的是句子碎片，追问时拿到的是上一问的词。
- 由代码检查“照搬台词”并退回：模型只是把引号去掉。
- 作答时按覆盖面退回、预算提示、重读拒绝、阅读计划：手写的进度规则只对样例有效。
- 固定的阅读步骤（“写作前先读梗概和最后几章”）、针对某类剧情的检查项、围绕某类问题设计的特征或输出字段（`CLAUDE.md` “禁止特判”）。
- 把没人读的表、别名表、“前作/续作”表加进知识库来帮模型：身份和先后由模型读原文确认。
