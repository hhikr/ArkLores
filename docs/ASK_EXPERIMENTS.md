# 剧情问答：试过的办法、表现与评估

> 截至 2026-10-19（分支 `ask-recall-eval`）。这里记**每一种试过的做法、量到的数据和结论**，包括失败的。
> 现在的流程怎么工作见 `ASK_AGENT.md`；仍开放的问题见 `KNOWN_ISSUES.md` §2。
> 早期轮次的逐次原始表格在 git 历史里（`git show 0b819ce:docs/AI_ARCHITECTURE.md`、`git show 29a5e8e:docs/R17_TOOL_AGENT.md`）。

## 0. 一页结论

**问答还没有达到想要的质量。** 结构（一个模型 + 通用工具 + 只追加的对话 + 代码核对出处）从 R17 起没有变过，它明显好于之前的分步流程；
之后的工作都在“让模型拿到该读的原文”上。按现有的测量，**第一步能给到的金标原文最多约 75–79%**，剩下的主要是这几类，都没有解决：

| 问题 | 现象 | 试过的办法与结果（详见下文） |
| --- | --- | --- |
| 概念题找不到原文 | 金标是剧情里顺带的一两句台词（“炎国人对感染者的态度”），问题里的名字不在那一行 | 场景卡（整张、按句）、检索块加前缀：都没救回或只救回 2 条（§5.5–5.7） |
| 取材后“够了就答” | 第一步给了 3 万字，模型常常一次工具都不调用就作答，不追查空档 | “没有查到”的查证（§5.4）只在模型自己声明空白时起作用 |
| 答案的先后顺序 | 活动和主线的先后写错（塔露拉一题把《我们明日见》排在第 10、13 章之前） | 原因之一是 v0.14.0 的库没有主线的时间，取材按上线顺序排时主线全排在最后；2026-10-19 重建的库补上了（`show_time`），**还没用真实模型复验** |
| 出处只核对“看没看过” | 引错人、引错词、直接接受提问里的前提 | 没有试过按内容核对；靠“复核”按钮 |
| 跨游戏推理 | “佩丽卡 幕后高层”一题 6 个会话全部 partial 或取消 | 没有专门处理（不写人物分支） |
| 成本与耗时 | GLM 一题 1–4 分钟；取材让第一轮的 prompt 多 5–15 万 | 没有专门优化 |

**不要再试的**（每一条都有数据，见 §6）：分步流程与摘要交接、手写进度规则、代码从问题里切词、固定阅读步骤、按题型分支、挑行（`pickLines`）、加大取材的前后行数、场景卡、检索块前缀。

## 1. 怎么评估

| 手段 | 内容 | 用在哪 | 注意 |
| --- | --- | --- | --- |
| 真机会话 | 开发者在手机上问的会话（`chat_sessions/` 的 JSON，0.14 起可经桥 `tools/phone_ask.dart` 实时看） | 发现问题 | 不可重复，只能对照 |
| 同链路 live 测试 | `test/live/ask_pipeline_live_test.dart`，驱动 App 的 `askChatProvider`，只换注入的 provider 与路径 | 改动前后对比 | 花钱；**单次运行波动很大**，比较两版要各跑几次 |
| 评测集（旧） | `test/fixtures/investigation_eval.json`，30 题草稿，标的是金标章节 | 拟定检索词的命中（§4.6） | 标准答案没人工审核过 |
| 历史问题集 | `test/fixtures/history_questions_eval.json`，玩家实际问过的 37 问 | 0.14 整体回归（§4.8） | 只看“答完、没崩、成本”，不判对错 |
| 离线召回测试 | `test/live/recall_eval_test.dart` + `test/fixtures/recall_eval.json`：日志题 26 题、68 处手标金标行 + 旧调查题 29 题；只量**第一步**（第一次模型调用之前）给模型看过的原文里有没有金标行 | 第 0 期起所有检索改动 | 免费（查询向量已缓存）；只量“给没给到”，不量答得对不对 |

- **answered 的比例不是质量指标**：answered / partial 取决于模型自己有没有声明遗漏。同一道按人物问的题 16 次运行里，改前 4 次全是 answered、其中 3 次漏了两部没有声明。
  比较两版代码看答案里有出处的故事集、出处是不是讲这件事的行。
- 召回测试的金标行是“答这题必须读到的那一行”，一题多处；“命中”= 第一步展示过其中任意一行。

## 2. 阶段一：分步流程（R0–R16，2026-09 至 10-03，已全部删除）

做法：把问答拆成多个角色——规划器（看压缩后的状态决定下一步）、提取器（把读到的原文变成笔记）、writer（从笔记和材料里选段落写答案），每步重建提示词。

| 轮次 | 做法 | 表现 | 评估 |
| --- | --- | --- | --- |
| R1、R3 | schema 3 确定性覆盖层（实体出现表、章节画像、稀有词）+ 专用工具；调查 Agent 与“结论门槛” | “某角色在哪出场”不再依赖措辞 | 覆盖层后来没有代码读（0.14 删除，库从 679 MB 降到 299 MB）；“凶手类”结论门槛是特判，R13 删除 |
| R5–R7 | 会话 JSON 持久化与回放；分层记忆；记忆并入 system | 真机问题可复现；98% 的迭代丢 `Thought:` 前缀 | 持久化留下；记忆结构随分步流程删除 |
| R8–R11 | PlannerLoop 三角色；自动消歧；SEARCH 重复终结补丁 | 同名实体让 SEARCH 死循环，补丁只修终止 | 补丁只对样例有效，R13 全删 |
| R12 | 证据笔记、writer 读原文并核对引用、可选向量召回、同链路 live 测试 | deepseek-flash：特蕾西娅一题 23 步 / 82 s / 10.7 万输入，正确；中期评测有引用的答案 6% → 100%，金标章节召回 0 → 0.63 | 引用核对和 live 测试留下 |
| R13 | 三种模式统一成一条流程；删除全部问题类型特判；代码判定状态 | 5 次验收：宽问题 24 步内常常读不全（梗概题跑满预算、结局写“未覆盖”） | “禁止特判”成为硬规矩（守卫测试） |
| R14 | 故事目录与官方梗概、OUTLINE、追问承接上一轮原文 | 特蕾西娅两问：11 次运行，最后 6 次全部指出博士的作用，每次两问输入约 13.5–14.5 万 | 目录留下；同一题要连续几次满足标准才算数 |
| R15 | 读音近似名、全部故事集总览、问题人物总览常驻状态 | 错别字（缪因 → 谬因）能找到；“全部故事”能跳出局部 | 近似名留下 |
| R16 | 真流式、按角色设思考档位；开局阅读计划、重读阶梯、作答前充分性检查与复核 | 塔露拉一题要 16 次运行才稳定：最终 35–39 步、52–61 万输入、97 s；重复步占 20–60% | **补丁越多越只适合样例**：每条规则都是为某次失败加的，换个问题就变差 |

**结论（R17 的起因）**：开发者让几个通用 agent 只凭一句提示词直接读同一个库，结果全都比 R16 好。它们的共同点：先用聚合查询看全局、整章读、读原文的模型就是写答案的模型、对话只追加（97% 命中缓存）、没有进度规则。
分步流程的根本问题是**信息每多一次交接就丢一部分**、每步重建提示词无法命中缓存。

## 3. 阶段二：工具型 Agent（R17–R18、v0.10–0.13，2026-10-03 至 10-09）

### 3.1 R17：一个模型 + 通用工具

工具：只读 `sql`、`grep`、`read_story`（整章）、`find`、`outline`、`similar_names`，之后加并行子 agent `delegate`。代码只核对出处。

| 问题（deepseek-v4-flash，不思考） | R16 | R17 |
| --- | --- | --- |
| 塔露拉在切尔诺伯格事件之后做了哪些事情？ | 35–39 次调用、52–61 万输入（基本未命中缓存）、97 s | 11 次、35.2 万（缓存 29.8 万）、35 s；4 个金标章节全读 |
| 切尔诺贝利（写错）之后塔露拉做了什么？ | 45 次、40.7 万、71 s，只覆盖到 9-21 | 14 次、37.0 万、47 s，写明“库中写作切尔诺伯格”，覆盖到 17 章 |
| 缪因是谁？ | 46 次、19.7 万、55 s | 8 次、5.9 万、19 s |
| 整理凯尔希在主线第 9–15 章里的主要行动 | — | 57 次、173 万（缓存 149 万）、132 s；派 5 个子 agent |

**评估**：未命中缓存的输入降到 1/5–1/10，耗时减半，全面优于 R16。这是现在的骨架。单次运行仍有波动（第一次塔露拉漏了 EG-7）。

### 3.2 R17b / R17c：答案的写法

| 做法 | 表现 | 评估 |
| --- | --- | --- |
| 提示词要求不照搬台词、不提库和文件名 | 引号内字数占比 19.8% → 15% | 不够 |
| 答案只输出 JSON（`entries` + `cite`），代码转成 markdown | 引号占比 15% → 0.5–1.4% | 留下 |
| 代码检查“照搬台词”并退回 | 真机上退回一次，模型只是把引号全去掉（连被问的词） | 2026-10-10 删去 |
| 提示词只用文字描述出处格式 | GLM 把 `cite` 写成平铺数组，手机上 52 处出处全被丢掉 → not_covered | 改为给完整 JSON 骨架 + 解析器容错 + 丢弃计数后退回（v0.10.6） |

### 3.3 R18：审稿与按阶段整理

| 做法 | 表现 | 评估 |
| --- | --- | --- |
| 审稿子 agent 逐条怀疑细节 | 5 个问题，白查一轮 | 改成只问故事层面（后来的揭示、其他故事、是否答非所问），最多三问 |
| 故事层面的审稿 | 安多恩一题：重写后开头交代“整段经历发生在梦境里”；但提什么有波动，依赖模型对作品的记忆；调用数多出一截（17 → 33） | 有用但贵；0.14 起改为答后的“复核”按钮 |
| 按阶段整理（`stages` + 条目号，代码合并出处） | 出处一个不丢；长答案变成几段 | 留下，0.14 起是答后的“提要”按钮 |

### 3.4 换模型与速度（v0.10.6–0.10.7）

- 换 glm-5.3-flash：安多恩一题 16 次 / 51.7 万（缓存 89%）/ 263 s，约 $0.03。
- 速度：带工具的调用有 4.5–8 s 底噪；写答案文本占 ~54% 时间；本地数据库 ~17%（`story_lines` 没有 `(story_id, line_index)` 索引，读一章 0.45 s）→ 加索引后读章 0 ms。
- 并发：当时同一个 key 同时发 5 个请求全部 200（2026-10-04）。

### 3.5 0.12–0.13：两个游戏与 Wiki

- 0.12：两个库合成一个检索面（`MultiGameRetrieval`），所有 id 带 `ef/`。
- 0.13：`wiki_search` / `wiki_read`，Wiki 段落作为第三种出处，同一套核对。没有规则时模型在库里查不到也不去查 Wiki；加一条“换写法仍查不到先查一次 Wiki”后会查，但一题 49 次调用、104 万输入。

## 4. 阶段三：0.14 重构（2026-10-09 至 10-11）

依据：v0.13.0 真机 10 个会话、16 轮问答——3 轮失败、4 轮取消，一题 1.5–24 分钟、16–149 万输入，156 次工具调用里 26 次（17%）出错。骨架不变，改外围。

### 4.1 可靠性（全部留下）

| 做法 | 起因 | 表现 |
| --- | --- | --- |
| 问答用自己的数据库连接 | 别处以同一路径打开再关闭，把问答的连接也关了（`database_closed`） | 不再出现 |
| 工具调用守门（`tool_call_gate.dart`） | 中转站把两个调用拼成 `{…}{…}`；非法参数原样存进历史，服务商拒绝整题 | 不再出现 |
| 空回复只对一轮降级 | 一次空回复就整题改文本协议 | — |
| 取消立即断开、当场记用量 | 取消后等下一个事件，用量记错 | 已发出的 HTTP 请求仍在后台跑完（`KNOWN_ISSUES.md`） |

### 4.2 统一检索 `search`

一次查两个游戏的剧情（向量 + 关键词，RRF 融合）、资料和 Wiki，按来源分组；打印的行算读过。
真实模型验收（GLM）：海嗣一题 0.13.0 真机 76/53 次调用、148/149 万、740/1444 s → 0.14 13 次、26.4 万、155 s。**留下。**

### 4.3 第一批查找：从代码切词到模型拟定

| 做法 | 评测集 29 题里至少列出一篇金标 | 评估 |
| --- | --- | --- |
| 代码用问题原文检索、从问题里切名字和短语 | 16/29（只有关键词） | 切出“龙门相撞”“死负责”这种原文不会出现的碎片；追问时拿到上一问的词。**删除** |
| 一次独立的小调用拟定检索词（只看问题） | 21/29（只有关键词）、25/29（带向量） | 留下。约三分之一的题会带进很泛的词（阵营、种族、主角名）或资料种类的词（“档案”），提示词说了“不写”仍会出现 |
| 拟定可以选 `outline`、`wiki_search` | 按故事集问的题：12 次 / 34.1 万 / 漏一部前作 → 8 次 / 15.4 万 / 四部前作都讲到 | 留下；玩家没提 Wiki 时也会写一条 `wiki_search` |

### 4.4 读资料、出处与退回

| 做法 | 起因 | 表现 |
| --- | --- | --- |
| `read_record` 读资料全文 | 用 12–14 次 `sql` 才读完一份档案 | 艾丽妮一题 20 次 / 35 万 / 120 s → 5 次 / 3.7 万 / 72 s |
| 资料向量（`record_chunk_vectors`） | 换了说法问“是谁说的”找不到语音 | 修前 8 次 / 11.1 万 → 修后 3 次 / 2.4 万 |
| 出处只读过一部分时裁成读过的段 | 检索只列了几行，引用整段就被整条删掉 | 真机 14 题里 9 题触发 |
| 退回 = 整轮回档 | 退回的错答案留在对话里 | 真机触发过；界面只留一行状态 |
| 答案 JSON 的容错（提前闭合、没转义的引号、几份答案取最后一份完整的） | 13 条只显示第一句；引号截断后只剩两成 | 用原始回复离线重放验证，真实模型没有再触发 |

### 4.5 让工具直接给原文（“指路不如直接给”）

| 做法 | 表现 | 评估 |
| --- | --- | --- |
| `search` / `grep` 写出词在各故事集的分布 | 按人物问的题，五部故事都讲到：改前 1/4 次 → 2/4 | 只写“在哪”，模型一半时候读完最相关的一篇就作答 |
| 加“各给一段”：分布里列出、最相关 5 篇没覆盖的故事集各给一段原文 | 4/4；输入约 2–3 倍（5–15 万） | 留下 |
| `search` 的 `near`（与读过的段落相近的段落） | 所有真实运行里模型从来没调用过 | 留着，没效果 |
| `outline` 末尾列相关的故事集（共有说话人 + 向量平均方向） | 见 §4.3 | 留下；库里没有数据说明谁承接谁 |
| 读资料时按向量指向相关剧情、读剧情时自动附相近段落 | 模型不用，只是加长结果 | 删除 |

### 4.6 没有结果的查找的上限

一个工具一问里没有结果满 6 次就不再执行（开发者 2026-10-11 要的，唯一的手写进度规则）。要查表的一题：31 次调用、47 万 → 13 次；库修正（复刻活动的关卡）后 6 次 / 10.8 万。**留下。**

### 4.7 其余

- 手册（表结构）从系统提示移到 `guide` 工具、随第一条 `sql` 附上：系统提示变短，没有发现副作用。
- 审稿、提要从提问选项改为答后按钮：17 题真机全程没开它们，答案质量都可以。

### 4.8 历史问题集（2026-10-11）

37 问（玩家实际问过的），GLM、Wiki 开、两个库：全部答完，47 分 39 秒，输入 516.6 万（缓存 377.6 万），answered 28、partial 9；
v0.13.0 真机上的失败、几十步、上百万输入都没有再出现。查出并改掉的：引号截断、`grep` 范围合并、括号里的出处、`wiki_search` 多词无结果、`grep` 截断后看不到剩下的、Wiki 超时、库里没有的人物被逼着凑出处。

## 5. 阶段四：统一重构（第 0–5 期，2026-10-18/19）

方向（2026-10-18）：**找原文由代码按索引一次找全、给齐；模型只读和写；中间不经过任何摘要；卡片、梗概只做定位，不当证据。**
每一期先过离线召回测试，再决定要不要进下一期。验收门槛：日志失败题的金标行出现在材料里 ≥ 90%；全部题的金标篇出现在清单里 ≥ 80%；材料字数中位数 ≤ 3 万、p90 ≤ 10 万；跨游戏题另一个库的金标出现 ≥ 2/3。

### 5.1 第 0 期：召回测试与基线

建了离线召回测试（§1）和查询向量缓存。日志题第一步的金标行命中：

| 方案 | 命中 | 字数中位 | 说明 |
| --- | --- | --- | --- |
| 0.14 只有拟定的检索 | 37% | — | 基线 |
| 只按锚点取材 3 万字 | 56% | 3.6 万 | |
| 拟定检索 + 取材 3 万字（**现行**） | 74% | 5.1 万 | 一条都没中的题 1 |
| 拟定检索 + 取材 4.5 万字（前后 2 行） | 76% | 6.6 万 | 唯一没有零命中题的方案 |
| 前后 4 行 3 万 / 4.5 万 | 66% / 74% | | 同样字数下前后行数越少越好 |
| 前后 8 行 4.5 万 | 69% | | |
| 宽取材 6 万 / 12 万（前后 8 行） | 75% / 85% | | 字数 2–4 倍 |

### 5.2 第 1 期：按名字取材（`gather`，留下）

拟定的调用另写最多 6 个锚点（问题涉及的名字）；检索之后代码调用一次 `gather`：锚点出现和说话的行，前后各 2 行，按锚点稀有度和同场打分，每故事集先三篇、每篇 ≤3000 字、共约 3 万字，按上线顺序排列，登记为已读。

真实模型（glm-5.3-flash）：

| 题 | 取材前 | 取材后 | 评估 |
| --- | --- | --- | --- |
| 贫民区的结局（slum_fate） | 答成“原文未交代” | 答对；6 次调用、prompt 21.5 万、137 s | 有效 |

### 5.3 第 1 期 S0：追问时重读上一答引用的原文（留下）

### 5.4 第 2 期：查证“没有查到”（留下）

答案 JSON 可以带 `missing`（没查到的事 + 最多 3 个相关名字）；答案通过核对后代码用这些名字取材约 1.2 万字，只留没读过的段落，有就交回重写一次。

### 5.5 第 2 期 S5：按段挑行（`line_picker.dart`，默认关，**不要打开**）

### 5.6 第 3 期：场景卡（P3 / S2，**不推全量**）

## 7. 还没试过的方向（只是想法，没有数据）

- **让模型在读的过程中继续查**：剩下的金标多在已经给到的故事集里、但不在给到的那几行里。比起在第一步给更多，更可能有效的是让模型读完取材后自己顺着线索检索；现在它常常“够了就答”。改提示词之外的办法（不能是手写进度规则）还没想清楚。
- **按内容核对出处**：代码现在只查“看没看过”。
- **跨游戏的身份推断**：通用机制（例如工具结果给出实体在另一游戏里的条目），不写人物分支。
- **用户资料（《大地巡旅》）作为第三档来源**：开发者的项目目标之一，需要先定可信度档位（原文 = Wiki > 用户资料 > 推测）和答案怎么标来源。

## 8. 检索范围、引用登记与阅读错误（2026-10-24，未发布）

### 8.1 可确定复现的工程问题

- `search(collection: ...)` 原先先取全库前几名再过滤。范围内确有结果时，也可能因全库候选占满而返回空；现将故事集范围下推到关键词和向量检索的排名之前。
- `search` 和 `grep` 曾把最后没有输出的片段登记为已读；`read_story` 用首尾范围登记，会把不存在的中间行也算进去。现只登记真正显示的行，`grep` 在完整行之间截断并给续读位置。
- 标题、分段、步骤、任务、未定位提示、教程、分隔和梗概不再进入可引用账本。SQL 即使没选择 `kind` 也回查原始行种类；`missing` 回查同样过滤。超过 1000 行的引用不再只检查开头。
- 命中向量块原先只展示前 8 行，改为 12 行仍不够：本机明日方舟库有 7439/55719 个块的行号跨度超过 12，且其中实际有超过 12 条正文。迁移后的块范围不能靠固定行数推断；现读实际起止范围，单片段最多 4992 字符，超出时标明未展示尾部。没有扩大整份结果的字数预算。

以上问题用生产 schema 的离线回归确认。它们修复检索和引用边界，不证明原文支持模型的每一句话。

同一份缓存查询向量和当前两库上的离线对照：拟定检索加取材均命中 45/68（66%），26 题中 14 题全命中、2 题零命中。最初基线展示字数中位 51857、p90 66190；按实际块范围显示并加入节选边界的实验版为 58151、73467（节选标记随后撤下）。材料更多，但聚合金标召回没有改善；§5 的历史 74% 不能充当本轮基线。

同一模型 `glm-5.3-flash`，本机重建的明日方舟库与 0.16 终末地库，Wiki 开启。每次逐题运行，先检查结果再决定下一次；没有执行全批付费评测。下表用量是模型输入加输出，不含查询向量。

| 题与条件 | 模型调用 | token | 结果 |
| --- | ---: | ---: | --- |
| 炎国与感染者，修改前 | 4 | 142342 | 局部言行被概括为全国态度与制度 |
| 同题，修复检索后 | 9 | 379796 | 读到更多出处，但仍过度概括，并补写缺乏依据的跨游戏关系 |
| 同题，加通用证据边界提醒 | 5 | 195743 | 仍把陈的话归到魏彦吾；部分正文引用了不支持结论的段落 |

“深度思考”对应应用 `ReasoningLevel.low`，在 GLM 上映射为 `reasoning_effort: high`。这次没有再把潜意识画面写成事实，但初始 search 也恰好给到了说明性质的前文；不能把这一点归功于思考档位。单次答案的变化还受拟定检索的随机性影响。

已确认的错误分两类：一类是材料缺少语境，例如第 14 章片段从 L124 开始，L115–123 的性质说明没有展示；另一类是原文已经给出却读错，例如带说话人的台词、明确的“一个月后”计划和先后关系。继续增加召回不能单独解决后一类。

### 8.3 独立出处核对的边界

用两份已保存答案及逐条引用的原文做本地核对，每条补前后 3 行，未加入产品流程。两次分别消耗 10935、17906 token，指出错归说话人、引用不含所述事实、错用地区资料等问题。但上下文本身不完整时仍会漏掉关键性质说明，也没有找出所有过度概括；不能作为可靠的自动放行依据。

答后“复核”仍由用户点击触发，没有增加自动审稿调用。

### 8.4 固定初始材料重放

重用默认档塔露拉题的 4 个拟定工具结果，不再运行拟定、检索或向量调用。每个变体只发一次请求，返回的工具调用也不执行。三组都是默认思考档位；这是生成行为的对照，不是端到端验收。

| 变体 | token | 返回后续工具调用 | 人工核对 |
| --- | ---: | ---: | --- |
| 当前格式 | 41282 | 0 | 仍有无出处概括、错误时间关系 |
| 每条先输出 cite 再输出 text | 41787 | 0 | 把早年的雪原经历写成龙门战败后的经历；所选引用没有阻止时序错误，不采用提示词改动 |

前两组的用户问题、工具参数和工具原文完全相同，用摘要校验一致。节选组只插入边界说明，原文逐行保持不变。每组只有一次，不能据此比较总体错误率；它们都没有通过已知失败点的最低要求，未继续扩批付费。

实验另暴露了流式 JSON 解析的独立错误：合法条目把 `cite` 放在 `text` 前时，引用会先于正文显示。此兼容问题已经修复，两种属性顺序得到相同布局，正文仍实时输出；该修复保留，正式答案骨架顺序未改。

## 9. 0.21：减少 token 消耗（不降低质量，2026-10-27/28）

样本：开发者真机的一问（盘点乌萨斯女大公，glm-5.3-flash，深度思考，Wiki 开，两个库），34 次调用、累计输入 3,152,773 token（缓存命中 96%）。
**累计输入 ≈ 调用次数 × 平均上下文**：聊天接口每次重发整段对话，所以省的路只有两条——少往返，或让每次的上下文小一点。只允许不减少模型能看到的原文与信息的做法。

离线回放（`test/live/token_replay_test.dart`，固定历史模型回复、执行真实工具，免费）：

| 改动 | 累计输入字数 |
| --- | ---: |
| 工具结果之间去重（`search`/`gather`/`grep` 查 `ContextLedger`） | −4.20% |
| 补充资料来源说明一问只印一次、`search` 每次都印的四句移进工具说明 | −0.95% |
| 提示词去掉过时、矛盾、重复的说法（前缀 −374 字） | −0.24% |
| 估算：模型一章一次读完（`ranges`） | 约 −27% |

把所有工具的报错、截断、分支提示都挪进工具说明的一版撤回了：工具说明每次请求都发，挪进去的若很少出现就是净增加，报错和截断时“下一步怎么做”也要写在结果里。只挪每次成功都会出现、且常被调用的句子。

真实模型（glm-5.3-flash，深度思考）：

| | 0.20 | `ranges` 与读整章说明之后（两次） | 提示词修改之后 |
| --- | ---: | ---: | ---: |
| 女大公：调用 / 累计输入 | 34 / 315 万 | 13 / 81 万、11 / 67 万 | 15 / 83 万 |
| 主循环里一轮发多个调用 | 0 / 28 | 7 / 9、6 / 7 | 6 / 12 |
| 同一章分几次读 | 6 章 17 次 | 仍有 3–4 次的 | 基本一次（4 次用 `ranges`） |
| 答案 | 27 条 / 4,052 字 | 17 条 / 2,254 字、25 条 / 2,830 字 | 20 条 / 2,261 字 |

- 省下的主要来自**一轮发多个调用**；一章一次读完在提示词修改后才基本做到，但那一次 `grep` 多了，累计没有再降。每问只跑一两次，模型每次调多少工具、读多少章的波动比改动之间的差别大。
- 答案主干与评价都在，正文比 0.20 短（55–70%），少些引语与细节；0.20 只有一次记录，没量过它自己的波动。开发者看过后接受。
- 塔露拉（切尔诺伯格之后）：28 万（6 章）→ 提示词修改后 43 万（8 章，每章读一次，答案多了维多利亚一段）。
- 深度思考：思考约占输出的四分之一，随对话重发的思考几乎都命中缓存，约占整问费用的 3–6%，0.21 起默认开。

没做的（有损，要做先问开发者）：台词行只在换说话人时写 `[说话人]`（行首占台词字数的三分之一）、不重发以前的思考、分布里泛词写短、同一批并行调用之间去重、拟定用更小的模型。
